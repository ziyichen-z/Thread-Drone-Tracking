# 多角色协作工作流

本文定义本仓库的共享工作状态、角色边界、交接物和完成门槛。所有角色
共享同一份文件系统日志，但各自的对话上下文并不自动共享，因此任何
关键结论都必须落到仓库文档中。本文只写现行规则；各条规则的来历与
修订史见 `docs/workflow-changelog.md`。

## 适用轨道

本仓库有两条工作轨道，**缺省是研究轨道**：

- **研究轨道（缺省）**：所有既有 work ID、`P1-*` 研究工作项与里程碑
  M0–M7 及其提案、复核、Unity 证据，继续完整适用本文全部条款。
  工程轨道生效（COORD-010，2026-09-07）之前的历史实现与复核不回溯套用
  新规则。
- **工程轨道（`engineering-v1`）**：仅当提案头部逐字写有
  `Workflow: engineering-v1`（该行只是申请）且经接受角色在 `ACCEPTED` 时
  写明裁定后生效，细则见 `docs/engineering-workflow.md`。
  没有该行的提案一律走研究轨道；路由不明时按研究轨道处理，不得由实现或
  复核角色临时改判。

工程轨道是**减法，不是豁免**。以下条款在两条轨道上逐字相同，不因工程
定位放宽：§1 的角色边界与越权禁令、§3 的状态门语义与 `DONE` 判据、
§2 的轮次命名及各计数上限、§4.3.3 的接受角色核对轮、§4.4 的
复核开轮资格与 finding 分级、§7 规则 0 的执行轨道纪律与 Gate-echo。
工程轨道的 K1–K5 必经停点每个都保留接受侧只读核对轮与独立复核；`DONE`
仍须实现证据 + 独立复核 + 相应 Unity/硬件证据（纯离线 `UNITY_NA` 须经
复核角色附议）。`CLOSED_*` 只表示停止该范围的工作，在任何轨道上都不
替代验收 `DONE`。

## 1. 角色与责任

| 角色 | 核心责任 | 必须交付 | 不应越权 |
|---|---|---|---|
| 构思（ideation，历史名 Claude Fable） | 功能构思、研究假设、备选方案 | `docs/proposals/<work-id>-*.md` | 不把提案直接写成已接受设计；不判定实现通过 |
| 接受（acceptance，历史名 Codex 审查半边） | 设计审查、取舍、实现后异源候选核对（§4.3.3）、关闭/返工归因 | 提案决策、正式设计更新、核对表、`implementation-status.md`（含「范围外已知缺陷」账本） | 不写实现代码；不给实现签发独立复核；核对轮不跑测试、不改实现、不因读码新增 BC 行 |
| 实现（implementation，历史名 Codex 实现半边） | 接口落地、代码与自动测试 | 代码、测试证据、复核范围、状态更新 | 不自行重新解释 binding clarifications；不签发独立复核 |
| 复核（review，历史名 Claude Sonnet） | 新鲜上下文重读真实代码，独立检查语义、边界和测试覆盖 | `docs/reviews/<work-id>.md` 与明确 verdict | 只在一次性 worktree 接触实现代码；发现问题交回实现角色，一行也不许修 |
| 辅助（chore，无门权限） | 滚动归档、代录、检索、可选预筛 | 非权威支持产出 | 不改任何 gate 结论、verdict、决策与代码 |
| 调度（supervisor，COORD-015） | 接力调度（每路同一时刻至多 1 个写仓库角色，COORD-019）、提交后事实核查（非权威）、决策信封内有界代拍、检查点摘要、COORD 起草（节流） | `docs/evidence/supervisor-dispatch.jsonl`、账本代拍/撤销/否决条目、状态板核查 Log | 不写运行时代码/配置/测试/工具与复核文件；不签发门与信封；不可代拍事项直达用户（COORD-015 §5.2） |
| 用户 | 在真实 Unity 编辑器/场景中执行验证并反馈；签发关键授权 | Unity 实际结果、报错、截图或运行产物；`docs/authorizations.md` 条目 | 不需要手工维护所有文档；可由接受或辅助角色代录反馈 |

角色名称描述的是当前分工，不绑定永久模型或产品；历史记录中的
Fable/Codex/Sonnet 指当时的同名分工，不回改。角色变化时只修改分工表
和 `docs/roles/` 细则，不改变证据门槛。
工程轨道不改变本表：职责与越权边界在两条轨道上完全相同，变的只是交付物
形态（短任务合同、`AC-n` 验收项、按 K1–K5 设停点）。工程轨道下仍是实现
角色写代码与测试，接受角色做范围决策、只读核对与收口，复核角色不修代码
也不复核自己的实现，用户给出关键授权与 Unity/硬件反馈；接受与复核角色在
任何轨道上都不获得运行时代码的写权限。

### 1.1 模型池映射与档位规则

| 预算池 | 档位画像 | 承担角色 |
|---|---|---|
| Fable 池（Claude Code，最强档） | 高智力、突发消耗 | 研究轨道构思、复核、DR-* 设计审查 |
| Codex 池（Codex CLI，中档、token 最少） | 判断密集、量小 | 接受 |
| Claude Opus 池（Claude Code，大量程） | 高吞吐实现与常驻调度 | 实现、supervisor（COORD-015 池重分配；Cursor `/coding` 保留为遗留手动入口，U8）、工程轨道构思 |
| Sonnet 池（Claude Code，最便宜档） | 便宜量大 | 辅助 |

- 复核者档位不得低于实现者；复核池耗尽时宁可等待或降到与实现者同档，
  永远不用最便宜档。
- 判断密集节点（提案接受、停点确认、归因）不放进最便宜池。
- 研究轨道的构思与复核共用最强池：二者必须是不同会话；DR-* 审查会话不得是相关
  提案的作者会话，优先由用户督跑新会话或使用外部强模型。
- 工程轨道沿用同一池映射与档位规则，唯一差异是构思跑 Opus 池：不新增常驻角色，复核档位不得低于
  实现者，工程任务合同的撰写与接受仍属判断密集节点，不放进最便宜池。

## 2. 统一工作 ID

每项功能从构思到关闭使用同一个 ID：

```text
P1-<AREA>-NNN
```

`AREA` 建议使用 `M0`、`SCENE`、`SENSOR`、`TRACK`、`EVAL`、`CTRL`、
`SEARCH`、`PLAN`、`VLM`、`DEPLOY`。例如：`P1-TRACK-001`。

- 纯协作/文档事项可用 `COORD-NNN`。
- Unity 用例使用 `UT-<work-id>-NNN`，例如 `UT-P1-TRACK-001-001`。
- 同一 ID 必须出现在提案、状态看板、复核报告、Unity 记录和里程碑证据中。
- **轨道标注**：走工程轨道的工作项在提案头部元数据区逐字写
  一行 `Workflow: engineering-v1`；没有这一行即研究轨道，本文全部条款适用。
  轨道在提案接受时确定，实现或复核期间不改轨；确需改轨按 §4.2 以新 work ID
  重新提案（既有 work ID 不得追加该行，见 `AGENTS.md`「工作流轨道路由」）
  并由接受角色记录决策。工作 ID 的命名规则两条轨道相同。
- **轮次命名**：三类轮次分开计数、分开命名：设计轮 `D<n>`
  （接受角色审提案，§4.2）、核对轮 `C<n>@<停点>`（接受角色的合同符合性
  核对，§4.3.3）、复核轮 `R<n>@<停点>`（独立复核，§4.4）。提交信息主题以
  `<work-id> D2` / `<work-id> C1@<停点>` / `<work-id> R2@<停点>` 开头；`<停点>`
  是提案停点列表定义的 ASCII 短名（如 `stageA`、`pilot`），每个停点定一次，
  交接行与提交信息逐字复用。
  §4.2 退修上限只数 D 轮，核对轮每停点 ≤ 1 次退回，复核 `REWORK_REQUIRED`
  每停点 ≤ 2 次，三个计数器互不合并。存量「接受轮 N」记录不回改。

## 3. 状态门

标准路径：

```text
PROPOSED
  -> ACCEPTED
  -> IMPLEMENTING
  -> IMPLEMENTED
  -> REVIEW_PASSED
  -> UNITY_PASSED
  -> DONE
```

可选分支：

- 构思审查：`REVISION_REQUESTED`、`REJECTED`。
- 独立复核：`PASS_WITH_NOTES`、`REWORK_REQUIRED`、`REVIEW_BLOCKED`。
- Unity 验证：`UNITY_FAILED`、`UNITY_BLOCKED`、`UNITY_NA`。
- `PASS_WITH_NOTES` 只允许无阻断问题时继续；注记仍要进入待办。
- `UNITY_NA` 仅用于不影响 Unity 运行行为的文档或离线工具，必须写明
  理由，且须经复核角色在复核文件中附议后方可用于关闭。

`IMPLEMENTED` 只表示代码和实现者侧检查已完成，不表示功能正确。
运行时功能只有在独立复核和用户 Unity 验证均通过后才是 `DONE`。
工程轨道使用同一张状态门表，不新增通过态。终止性 `CLOSED_*`（如
`CLOSED_INSUFFICIENT_DATA_WITH_PROVENANCE_GAPS`、
`CLOSED_PARTIAL_DELIVERY_ENGINEERING_HANDOFF`）表示停止该范围的工作，
不是验收通过，也不追认任何历史 verdict；使用时须在状态板同批写明保留或
转交的义务。

## 4. 六步流水线

### 4.1 构思角色：提出构思

在 `docs/proposals/` 创建提案，至少包含：

1. 问题和研究价值；
2. 输入、输出与受影响接口；
3. 算法或行为假设；
4. 与 v0.3 设计的兼容性；
5. 可证伪的验收条件；
6. 基线、消融、失败模式和资源风险；
7. 建议但不强制的实现范围；
8. 涉及真实归档或数据尺度的合同时，附一次只读真数据试跑的数字：行数、
   单条体积、内存投影、绑定率。

提交后把工作状态设为 `PROPOSED`，交给接受角色。
走工程轨道的工作项改交任务合同（`docs/engineering-workflow.md`）：目的、
范围、接口、验收项（稳定编号 `AC-n`，逐条附证据指针）、预算、限制，头部
写 `Workflow: engineering-v1`。上列第 8 要素在两条轨道都保留——涉及真实
归档或数据尺度的合同，没有只读真数据试跑数字就不冻结 schema 或数据尺度。
其余要素按工程任务实际需要收敛，但范围、接口和验收项不得留空。提交后同样
把状态设为 `PROPOSED`，交接受角色。

### 4.2 接受角色：设计审查

接受角色检查研究归因、接口一致性、几何/时序约束、指标污染、部署风险
和测试可行性，并在提案中写出一种决策：

- `ACCEPTED`：可以进入实现；必要时同步正式设计文档。接受时把
  binding clarifications 写成可逐条核对的条款——实现角色将按字面
  执行，歧义会被退回而不是被解释。
- `REVISION_REQUESTED`：列出可操作的修改要求，退回构思角色。
- `REJECTED`：记录拒绝原因，避免以后重复提出同一死路；限定为需用户授权
  的偏离。

没有 `ACCEPTED` 的新功能不进入生产实现；紧急缺陷修复可直接立项，但
必须在状态板中记录问题、范围和验收条件。带 binding clarifications 的
已接受提案本身就是"接受→实现"的交接物，不另设交接文档。

**提案文件的形态**：接受后的提案文件只承载已接受设计与
BC 表（每条一行：编号、条款、复核项、证明方式、标签、依据、日期；列定义
见下段）。实现期间的合同问题由实现
角色写在提案末尾的「待裁定」节，接受角色的答复直接成为 BC 表新行；不
追加轮次章节，轮次叙述进提交信息。提案文件超过 600 行即是信号：内容
放错了地方。

**BC 表结构与自检**：「复核项」列取闭集 `行为` / `几何时序` /
`边界失败` / `测试覆盖` / `文档一致`（依次对应 §4.4 五项清单，一格多值用 `/`
分隔）；BC 表下方固定一行覆盖声明 `复核项覆盖：`，五项逐一写 ✓ 或
`N/A（理由）`，即每项至少一条 BC 或 N/A + 理由；「证明方式」列写
`test:<模块.类.方法>` / `artifact:<路径或 ID>` / `cmd:<命令>` 三种前缀之一，
每条 BC 都能回答"用什么证明"，实现角色停点自证的证据指针用同一前缀；条款中的全称量词（全部/所有/任一/均须）必须
指向条款内已枚举或点名文件的闭集，否则该条退回重写。接受轮写入的行在「标签」列标 `BASE`；`ACCEPTED` 后新增的
每一行必须标 `CLARIFY` 或 `NEW_OBLIGATION`：`CLARIFY` 解释既有
条款，须引用被解释的条款号，允许用"指向具名提交中的具名工件"来枚举闭集；
`NEW_OBLIGATION` 只能源于实现角色的「待裁定」或复核的 `SCOPE_GAP`，禁止源于
接受角色自查代码，每个 work ID 上限 2 条，超出回用户。存量行不打标签、不
回改；计数自 2026-09-03 起。
**工程轨道的合同形态**：`Workflow: engineering-v1` 的工作项
不要求七列 BC 表，也不适用 `CLARIFY` / `NEW_OBLIGATION` 的标签与配额，改为
`AC-n` 验收项加一份简短决策记录。`AC-n` 承担 BC 在核对轮（§4.3.3）与复核
（§4.4）中的角色：逐条可核对、逐条给证据指针，指针仍用
`test:<模块.类.方法>` / `artifact:<路径或 ID>` / `cmd:<命令>` 三种前缀之一，
条款中的全称量词同样必须指向已枚举或点名文件的闭集。接口或验收项的实质
变化须先记录并经接受角色确认，不得边实现边解释扩大范围；同一范围第二次
退修后仍未收敛的，按本节退修上限上交用户，不无限循环。研究轨道的 BC 表
规则不变。

**真数据试跑先于合同冻结**：提案缺 §4.1 第 8 要素的
只读试跑数字时，接受角色不得冻结 schema 或数据尺度类的 binding
clarification。

**退修上限**：同一提案第 2 次
`REVISION_REQUESTED`（设计轮 `D2`）之后，接受角色不得自行发出第三次退修，必须上交
用户二选一：(a) 接受当前范围并逐条列出已知缺口；(b) 关闭为负结果
记录。决策信封 D1 在效且残留数非递增（本轮不多于上一轮；各轮裁定节末 `open_items:`
机读行，自首次退修裁定起每轮必填；COORD-015 §5.1/BC-12，COORD-016 §2.1/BC-1）、
且本提案已代拍少于 3 次时改交 supervisor，supervisor 仅可代选 (a)；残留数增加、
第 4 次、缺行或信封不在效时仍上交用户。计数按提案既有轮次追溯生效。采"上交用户"而非接受
角色自行改定，以保持提案作者与裁定者的分离。该计数只数设计轮 `D<n>`，
不与核对轮、复核轮合并。

### 4.3 实现角色：实现与实现者验证

开始时将状态设为 `IMPLEMENTING`，并在 Active handoffs 中声明主要文件
范围。binding clarifications 按字面执行；发现歧义或需要放宽验收条件
时退回接受角色，不得自行重新解释。完成时必须记录：

- 修改的关键文件和协议；
- 实际运行的测试/编译命令及结果；
- 未验证项和已知限制；
- 给复核角色的准确复核范围；
- 给用户的 Unity 用例或观察点；
- 逐条 BC 的证据指针：编号 → 具名测试、工件或命令（供 §4.3.3 核对轮
  逐条核对）。

满足这些条件后只能标记为 `IMPLEMENTED`。

**测试输出纪律**：开发期只跑 focused 套件；全套自动测试在停点
跑一次，输出写入 `docs/evidence/` 下该批次的证据文件，上下文只回显末尾摘要；
不带 `-v`。核对轮不跑测试；复核重跑 = focused 一次 + 每条阻断 finding 修前红/
修后绿一次。

#### 4.3.1 复核稳定候选停点

独立复核面向稳定候选版本，而不是每个小提交。实现角色整理候选与证据，
逐条自证下列条件，把自证结果（按 BC 编号逐条附证据指针）写入 `docs/evidence/`
下该停点证据文件的具名小节，交接行只写该文件与小节的指针，然后进入 §4.3.3
的接受角色核对轮；
核对完成后才把候选交给复核角色。核对轮是必经但有界的异源候选检查：固定
输出、同一停点至多退回 1 次，不另设停点确认。复核角色对自证条件不成立的候选
给 `REVIEW_BLOCKED`，不开轮、不计复核轮次。四项条件：

1. 当前 work item 的实现范围和接口已冻结；
2. 相称的实现者测试/编译通过；
3. 已知 Unity 失败已完成修复和聚焦复测，或明确属于复核角色才能判定的代码问题；
4. 复核文件、状态板、候选 commit 和未验证风险已更新。

已提交批次的写入归因不做机械检查；写入纪律由各角色收工的未提交自检
（§7 规则 7）与基础设施保护承担。

到达停点后，实现角色不得开始依赖该结果的新功能，只能整理证据并将候选
版本交给复核角色。若复核给出 `REWORK_REQUIRED`，实现角色修复并补齐证据
后回到同一停点并直接交回复核，不经核对轮；修复批次是否开新复核轮由 §4.4 的开轮资格
（PLAY_GOVERNING diff 非空）决定，阻断 finding 的闭合走 §4.4 的回归
测试闭合通道（触及 Play 治理门文件的修复必开闭环轮）。

本项目的强制停点为：

- M0 基础协议/评估器关闭候选；
- M2 首个反射层闭环候选；
- M3 世界系估计与机身规划闭环候选；
- M4 丢失升级、YOLOE 仲裁与遮挡实验候选；
- M5 冻结的全量评测流水线；
- 可选 M6 VLM 消融候选；
- M7 Orin 部署候选；
- 任何单独改变帧/控制协议、坐标或时间语义、主指标定义、安全约束、模型
  决策逻辑的 work item。
以上里程碑停点属研究轨道。走 `Workflow: engineering-v1` 的工作项改用
`docs/engineering-workflow.md` 的 K1–K5 必经停点：K1 帧/控制协议及坐标与
时间语义；K2 安全约束与控制命令；K3 模型决策、目标身份与重播种；K4 数据
划分/标签或对外指标；K5 对外发布候选。两套停点判据同源：凡改变帧/控制
协议、坐标或时间语义、主指标定义、安全约束或模型决策逻辑的改动，两条
轨道都必须停点，工程定位不构成豁免。涉及 Jetson/Orin、TensorRT/CUDA 或任何
板端硬件的工作不由 K1–K5 覆盖：无论哪条轨道都必须独立立项、独立说明设备与
执行额度，按上列 M7 停点处理，桌面量化或仿真结果不替代板端实测（可行性
探测可前移，独立立项与额度不减）。相互关联的触发可以合并成一个候选，
但合并后的候选仍须逐项说明覆盖了哪几个 K。每个 K 停点走与研究轨道相同的
次序：本节四项自证条件 → §4.3.3 接受角色核对轮 → §4.4 独立复核；已接受
任务合同范围内的日常小改自行 focused 验证并合并到下一个稳定停点，未经
复核的中间成果只记 `IMPLEMENTED`，不记 `DONE`。

§4.4 finding 的依据列闭集六值在工程轨道逐字沿用，**不新造 token**：依据列
仍写 `BC-n`，读作任务合同第 n 条验收项 `AC-n`，对应关系写在 finding 正文；
`IN_SCOPE_NO_BC` 读作「可达、在范围内但无 `AC-n` 覆盖」。其余四值及其阻断
语义不变，§4.6 的归因机械派生与「范围外已知缺陷」记债无须改动。
研究轨道的 BC 表规则不变。


当前执行范围是电脑端 Unity/Python 仿真。M7 以及 TensorRT/CUDA/Jetson
依赖只有在用户显式启动部署工作后才进入 active handoff；在此之前不得把
未安装 NVIDIA 栈记作 M0-M6 的环境阻塞。

纯文档、日志、测试补强和不改变行为语义的小修不单独触发停点，可并入下一
稳定候选。M2、M5 和投稿前的新鲜上下文设计审查仍是额外门禁，不能由此处的
代码复核替代。

#### 4.3.2 诊断验证通道与人眼保真检查

正式证据纪律核对哈希、计数与协议链，但不覆盖"渲染出来的东西对不对"
这类范畴错误。为此设两条通道：

- **诊断验证通道**：实现角色开发期可请用户辅助进行诊断性 Play 运行、
  渲染目检或样帧核对。诊断活动必须：明确标注为诊断；不创建、不消耗
  scenario/session/run ID；产物不进证据链、不作为任何门判定依据；
  发现的问题走正常返工渠道。批次条款中的"零 Play"约束正式采集与
  证据侧，不禁止本通道。
- **人眼保真检查（硬性）**：任何新渲染/采集管线在采集协议冻结或首次
  正式采集（以先到者为准）之前，必须完成一次人眼保真检查：至少 2 张
  样帧，由用户或当轮发令角色确认渲染对象与运行时外观/语义一致，结果
  （样帧路径、确认人、结论）记入该批次证据文件。未完成即为协议缺口，
  复核应列为阻断项。
- **反调参纪律不变**：正式门工件产出后，仍禁止依据门数字修改参数、
  帧集、阈值或测量对象；诊断通道不得用于在正式运行之间"试数"。

#### 4.3.3 核对轮：接受角色的异源候选检查

候选自证后、复核开轮前，接受角色必须重新检查一次稳定候选，命名
`C<n>@<停点>`。该步利用接受角色（Codex CLI）与实现角色（Claude Opus）的模型
异源性，寻找实现摘要或单一模型可能遗漏的合同偏差与高风险失败路径；它不是
独立复核，也不替代 §4.4：

- 输入：候选 commit、实现角色声明的完整候选 diff、已接受提案与 BC、按 BC
  编号逐条附的证据指针；缺少完整 diff 或任一必需指针即记 `证据缺失`。
- 读取范围：重读完整候选 diff，并可读取理解该 diff 所必需的直接关联代码和
  指针所指证据；核对实现是否忠实于设计/BC、失败路径是否遗漏、测试是否对准
  条款。不得运行测试、修改实现或把本步写成独立复核 verdict。
- 输出：提案固定小节 `## Contract conformance（核对表）`，只保留最新一版
  （不逐轮追加，轮次叙述进提交信息）。每条 BC 一行：编号、结论、理由；结论
  闭集 {满足, 不满足, 证据缺失}。理由为自由文本，必须点名支持该结论的 diff/
  证据指针或明确缺少什么。另可列「预复核关注项」，逐条指向具体 diff/代码；
  非 BC 问题只作为待复核主张，不由接受角色自定 finding 分级或依据值。
- 本步不得新增 BC 行；含未枚举全称量词的 BC 先按 §4.2 出 `CLARIFY` 行再核。
  接受角色不得因本轮读码自行产生 `NEW_OBLIGATION`。
- 上限：同一停点核对轮退回 ≤ 1 次，「不满足」与「证据缺失」同计。第 2 次
  仍有未满足项或未决关注项时，候选照交复核，核对表与关注项随候选作为待核实
  主张，由复核裁决。核对轮不计复核轮次。

### 4.4 复核角色：独立代码复核

**开轮资格与 PLAY_GOVERNING**：PLAY_GOVERNING 集合的
唯一权威定义 = `controller/`、`Assets/`、`tools/`、`tests/`、`config/`、
`ProjectSettings/`、`Packages/packages-lock.json`，加上该 work item
冻结集点名的操作单文件；其他文件只引用本定义，不复抄。新复核轮只在
`git diff <上一通过候选>..<候选>` 于 PLAY_GOVERNING 上非空时开启；
为空时禁止开轮，缺陷按下方 finding 分级通道处理。复核重跑范围为
focused 套件并记录测试树哈希；全套自动测试是实现者停点证据
（§4.3.1 条件 2）的义务，不再是开轮义务。

**finding 分级**：CLASS_1（改数字或结论）与 CLASS_2
（边界、失败路径、并发/原子性、真值泄漏）→ `REWORK_REQUIRED`。
CLASS_3 为**闭集**：拼写、格式、失效链接、已执行步骤的时态，以及证据
叙述中的计数或枚举——当且仅当它不驱动任何工具或操作员动作；凡涉及数值、
阈值、ID、判据、执行顺序、终态名的文字一律最低
CLASS_2，判据是"操作员或工具的行为会不会因这段文字而不同"。CLASS_3
不阻断：复核在复核文件给出逐字替换补丁（`controller/`、`Assets/`、
`tools/`、`tests/`、`config/` 一行不许改），由拥有该文件写权限的角色在
下一次提交应用，不开轮，不得改动任何数字、哈希、run ID、disposition。
**finding 路由**：CLASS_2/3 finding 由复核角色直接交回
实现角色；接受角色只在 (a) CLASS_1、(b) 复核或实现角色提出分级争议、
(c) 用户要求时复判。复判写在提案「待裁定」节之后的固定小节
`## Acceptance rulings（复判）`（每条一行：复核文件/轮次/finding、裁定、日期），
不另开轮；接受角色无 `docs/reviews/*` 写权限。

**范围判据与依据列**：CLASS_2 加范围判据。可达 = 触发
状态是提案、BC 或验收条件点名的，或生产入口能从已归档工件产生的。每条
finding 带依据列，恰填一个值（涉及多条 BC 时填主要一条，其余进正文），闭集六值：`BC-n`（可达且有 BC 覆盖，阻断）、`IN_SCOPE_NO_BC`
（可达、在范围内、无任何 BC 覆盖，仍阻断）、`SCOPE_GAP`（不可达的边界/失败
路径，独立非阻断标签，不进 CLASS_3 闭集，直接路由接受角色）、`上轮漏检`、
`上游漏检`（核对轮放过的字面不符）、`RED_LINE`（真值泄漏、人眼保真等红线，
永远阻断，不受增量轮的范围与轮次上限限制）。

**增量轮与双基线**：第 N+1 轮先读既有轮次。两个 diff 基线
并存，各管一件事：修复触及行 = `git diff <上一复核轮候选>..<候选>`，上一复核
轮候选由复核文件每轮 §0 的机读行 `round_candidate: <40 位 SHA>` 派生（每轮
必写，通过轮同时写 `passed_candidate`）；全量 diff = 相对上一通过候选，仍必做，
用途是核实声明范围与红绿验证，不作为本轮的阻断范围。新阻断只来自：修复
触及行上的 CLASS_1/2；旧 finding 闭合失败；`RED_LINE`；未改动行上标
`上轮漏检` 的 CLASS_1。未改动行上的 `上轮漏检` CLASS_2 不阻断本轮，改为阻断
下一个消耗性门：复核文件写机读行 `blocks_consuming_gate: <finding-id>`（不带
work ID；finding-id 逐字取该 finding 的标题编号，配对逐字相等），同一提交把状态板上受影响的消耗性交接改为
`PAUSED_CONSUMING_GATE_BLOCKED_<finding-id>`；`tools/check_docs.py` 拒绝任何
"存在未 release 的 blocks 行且 Active handoffs 有未暂停的 `Consuming=yes` 行"
的提交。release 只有两条路径：复核角色在后续轮红绿核实修复后，于同一复核文件
其后写 `releases_consuming_gate: <finding-id>`（按文件顺序配对，release 只关闭其
前面的 block）；或接受角色改标 `SCOPE_GAP` 时在 `docs/implementation-status.md`
「范围外已知缺陷」账本写一行、状态 `RELEASED_SCOPE_GAP`，`tools/check_docs.py` 把该行
视为 `docs/reviews/<Work ID>.md` 中该 finding-id 的 release（接受角色无
`docs/reviews/*` 写权限）。账本 release 按 finding-id 匹配、不看
顺序，因此被账本 release 过的 finding-id 不得再次 block，重开须用新编号。

**轮次上限与冻结集**：同一停点第 2 次 `REWORK_REQUIRED` 后，
未闭 finding 集合冻结，交接受角色逐条裁定「范围内必修」或 `SCOPE_GAP` 记债
（记入 `docs/implementation-status.md`「范围外已知缺陷」）。轮 3 检查范围 =
冻结集 + `RED_LINE` + 修复触及行上的 CLASS_1/2；轮 3 终局：通过，或回用户；决策信封 D2b 在效时回 supervisor，supervisor 仅可批准 1 次定向返工（限冻结集内具名 finding，`RED_LINE` 与 `blocks_consuming_gate` 未 release 的 finding 除外）；同停点第 2 次申请回用户。D2b 返工后按本节开轮资格分路：有资格开轮 4（终局：通过，或回用户）；无资格走本节阻断 finding 回归通道，任一未闭回用户。
锁的是未改动代码上的范围蔓延，不豁免修复自身引入的回归。复核返工直接回
复核，不经核对轮。复核重跑 = focused 一次 + 每条阻断 finding 修前红/修后绿
一次，输出写文件只回显摘要。

**阻断 finding 的闭合**：每条阻断 finding 绑定一条
修复前必失败的具名回归测试，闭合需四条同时成立：(1) fixture 由生产
路径产出——调用真实写盘函数或消费已归档真实 run 的字节副本，禁止
手工 mkdir / 手写 JSON 造状态；(2) 复核角色在下一轮以修前红/修后绿核实（在一次性副本中
`git revert -n <fix>` → 重跑该测试并观察失败 → 恢复）；(3) 修复若触及
Play 治理门（`analyze_m3_body.py`、`preflight_reanchor_env.py`、
`controller/run_log.py`）则闭环复核轮不得省；(4) 仓库里不存在可写断言的
finding 可标 `NOT_MECHANIZABLE`，闭合改为定点复看具名文件，不重跑全套。
不设例行的纯闭环复核轮。D2b 无资格路径（不开新轮）下，(2) 的「下一轮」指原复核文件的「回归核实」小节：复核角色在该小节逐条修前红/修后绿核实冻结集，全部闭合时写终局 verdict 与 `passed_candidate: <40 位 SHA>`，不新编轮号；任一 finding 未闭、缺终局指针、`RED_LINE` 未闭或 `blocks_consuming_gate` 未 release 均不得通过，回用户终局，不可再代拍。

**机读通过指针**：通过轮必须在 verdict 块写一行
`passed_candidate: <40 位完整 SHA>`；`REWORK_REQUIRED` 轮禁止出现
该行；存量不回改。"上一通过候选"此后一律由复核文件中最近一行
`passed_candidate` 派生，禁止手写进其他文档。

复核角色不依赖实现者的口头总结，重新读取当前代码、接受的提案、正式
设计和测试。复核只在一次性 worktree 中接触实现代码
（`git worktree add --detach`，收工删除），主工作树对实现文件保持
只读；必须 diff 候选与上一个通过候选并逐文件核对全部变更——实现者
声明的复核范围只是待核实的主张，不是复核边界。发现缺陷时唯一合法动作
是写入复核文件并给 verdict（CLASS_3 可附逐字替换补丁），把修复交回
对应角色；不替其他角色修改任何内容。操作细则见
`docs/roles/review.md`。复核至少覆盖：

- 行为是否满足验收条件；
- 坐标系、单位、时间戳、帧绑定和过期语义；
- 边界条件、失败路径、并发/原子性和真值泄漏；
- 测试是否真的覆盖声明的行为；
- 文档状态是否与代码相符。

结果写入 `docs/reviews/<work-id>.md`。若为 `REWORK_REQUIRED`，回到实现
角色；修复后在同一报告追加复核轮次，不删除旧发现。

### 4.5 用户：Unity 验证

用户按 `docs/unity-test-log.md` 中的用例在 Unity 中验证。采集开始前，
当轮发令的角色必须记录 `git rev-parse HEAD` 与 `git status --porcelain`
结果并写入本轮 Unity 日志条目：工作树必须等于被复核通过的候选，或仅
含白名单文档差异，否则 Unity 证据与复核证据不再对应同一代码。反馈至少
需要：

- Unity 版本、场景和配置；
- 实际操作；
- 预期与实际结果；
- `PASS`、`FAIL` 或 `BLOCKED`；
- 关键 Console 文本、截图或 `runtime/` 产物（若有）。

用户只需在对话中反馈，接受或辅助角色负责把反馈结构化写入日志并更新
状态板。失败时保留原记录，回到实现角色修复后创建新一轮验证。

### 4.6 接受角色：关闭或返工

接受角色只在最终通过轮消费复核 verdict（中间轮不消费），
汇总自动证据、复核 verdict 和 Unity verdict：

- 三者均满足验收条件：状态设为 `DONE`，同步里程碑证据。
- 任一失败：状态设为 `REWORK_REQUIRED`，明确责任人和下一步。
- 环境阻塞：记录 `BLOCKED` 原因、解除条件和已有证据，不伪装成完成。
- 终止某一范围而非验收通过时用 `CLOSED_*`，同批写明保留或转交的义务；
  历史负结果、主张上限，以及 `blocks_consuming_gate` /
  `releases_consuming_gate` 的配对关系不因终止而清除。
- 工程轨道使用同一套关闭动作与同一 `DONE` 双证据要求；工程工作项的关闭
  不得借用任何研究里程碑的通过名义。

**归因机械派生与记债**：从复核文件依据列派生：`BC-n` → 实现
错误；`IN_SCOPE_NO_BC` 与 `SCOPE_GAP` → BC 缺失（同一归属，按阻断性分计）；
`上轮漏检` → 复核标准；`上游漏检` → 核对轮；`RED_LINE` → 不进四类，单独列出，
修复仍由实现角色承担。`SCOPE_GAP` 与 §4.4 冻结集的记债统一落在
`docs/implementation-status.md`「范围外已知缺陷」节，按 work ID 列，每条带来源
复核文件与轮次、依据值、裁定日期、状态（闭集 `OPEN` 记债未修 / `RELEASED_SCOPE_GAP`
改标并 release 消耗性门 / `CLOSED` 修复经复核核实），由接受角色写；work ID 置
`DONE` 时随证据一并列出未闭条目。正常通过轮只机械汇总并关闭，不再做第三次常规候选检查；
只有 CLASS_1、分级争议、`SCOPE_GAP`、冻结集终局或用户要求才复判。四个度量按
work ID 记：核对轮退回次数（按结论拆）、复核
轮次（每停点）、BC 缺失类 finding 条数（`SCOPE_GAP` 与 `IN_SCOPE_NO_BC` 分计）、
`ACCEPTED` 后新增 BC 行数（`CLARIFY` / `NEW_OBLIGATION` 分计）。

### 4.7 周期性新鲜上下文设计审查

逐功能代码复核只能证明“代码是否忠实实现已接受设计”，不能证明指标、实验
归因或研究主张本身正确。为避免主指标天花板、信息不公平和消融混杂等设计级
问题，在以下节点增加独立设计审查：

1. **M2 关闭前**：检查首个闭环基线的指标是否有区分度、控制/感知边界是否
   公平、Unity 场景是否真的制造目标难点；
2. **M5 关闭前**：检查三轴消融、强基线、随机种子、置信区间和因果归因；
3. **投稿前**：检查论文主张与证据是否一一对应，负结果和实现简化是否诚实。

审查者必须使用新鲜上下文重读设计、结果和关键实现；不能是相关提案作者，
也不应是该设计的主要接受/实现者。由最强池的新开独立会话或用户指定的
外部审查者承担（构思角色与审查共用最强池时，审查会话不得是相关提案的
作者会话）。里程碑以终止性 disposition 收束但仍产生将进入论文的研究
主张时（如 `M2_NOT_CLOSABLE`），对应审查同样到期；推迟合并入投稿前
审查须经用户显式批准并记入状态板。报告写入 `docs/design-reviews/`，
允许 verdict 为：

- `DESIGN_AUDIT_PASSED`；
- `PASS_WITH_NOTES`；
- `DESIGN_REVISION_REQUIRED`；
- `DESIGN_AUDIT_BLOCKED`。

M2、M5 或投稿节点不得在设计审查失败/阻塞时标为关闭。该门是里程碑审查，
不要求每个小功能都增加第五位常驻角色。
工程轨道不新增第四个设计审查节点：K1–K5 停点按 §4.4 做相称检查即可。但
工程首版发布不得借用 M2/M5 的关闭名义，也不得声称完成被延期的研究设计
审查；日后恢复 M2、M5 或投稿研究时，本节三个节点的审查义务照旧到期，
推迟仍须用户显式批准并记入状态板。

## 5. 交接记录最小字段

每次跨角色交接都应在 `current-status.md` 表达以下信息：

```text
work_id:
from -> to:
current_gate:
requested_action:
scope/files:
progress:          # 已完成的最后一个动作 + 下一个待办动作
consuming:         # yes = 创建/消耗 scenario/session/run ID、Play 配额或 API 预算
acceptance/evidence:
known_risks:
```

`progress` 是执行轨道纪律（§7 规则 0）的强制字段：任何一条交接被暂停时，
必须凭该字段说清"执行到哪里了"，无须重读全部历史即可恢复。交接文字与
现实脱节时（前置条件已被其他工作项走完、引用的工件已作废），在同一批次
就地改正，不要留给下一个接手的角色。

详细内容留在提案、复核或 Unity 日志中；状态板只保留摘要和链接。

### 6.1 轻量按需读取

原提案、复核、证据和授权留在原路径；不复制或搬入新档案目录。当前状态提供
执行入口，原文件保存依据，Git 保存已提交版本中的重复叙述；这是读取与内容
归属规则，除 `docs/status-history.md` 这一个单向沉淀池与 `docs/parked-status.md`
这一份非活跃项台账外不新增归档系统，也不新增状态 token 或状态门。

1. **开工先读当前结构。** 在 `current-status.md` 完整读取 Current state、
   Role assignment、Active handoffs（含暂停行）、Immediate next actions、
   Active constraints and decisions、Upcoming design audits；按 work ID 查读
   本项及其依赖/交接引用项的 Gate board 行。首次定位可用 `rg -n '^## |^### '`
   获取章节位置，再读取所需区段；不要求每次展开整个 Gate board 的历史叙述
   或整个 Log。非活跃项（`PAUSED`/`ENDED`）的门值与未闭义务只在涉及该项时查
   `docs/parked-status.md`（含 YOLOE simulation/deployment split 与常设指针）。
2. **沿任务读依据。** 复用代码、数据、场景或旧指标，先读
   `implementation-status.md` 的「COORD-010 — 工程继承清单」与
   「范围外已知缺陷」账本，再读涉及的设计/提案/复核/证据章节；引用旧结论、
   恢复旧工作或追查缺陷时，展开对应历史和授权。当前处置优先于历史条目中的
   当时下一动作；找不到来源、范围不明或内容冲突时扩大读取，不由摘要补推结论。
3. **状态板保留什么。** 当前动作、门、未闭义务、复用限制与冻结主张保留摘要
   和来源；仅解释已闭合过程的重复叙述可按 chore 细则压缩。按需入口只写
   “何时读取 → 原文件及章节/条目标识”，不建立 `docs/parked-status.md` 之外的
   另一份状态表。活跃项的未闭义务留在状态板；非活跃项的未闭义务随该项移入
   `docs/parked-status.md`（事实源），状态板一行索引指明去处。相关性或义务是否
   闭合不由 chore 自行裁定，无法确认时保留原文并交负责角色。
4. **历史保存。** Gate board 是活跃项与暂停项（一行索引）的机检权威表；`ENDED`
   行整行移入 `docs/parked-status.md`「已终止（ENDED）」表，不迁往他处；旧 Log
   只有满足 chore 的删除条件、保护期与删除节奏才可移除。删叙述前确认它已在
   Git 已提交历史或明确引用的原文件中保存；未提交且尚未沉淀的文字不能声称
   已由 Git 归档。不改写原复核、失败证据或授权，不恢复按月搬运。
5. **必经检查不缩减。** 各角色要求完整读取的候选 diff、BC/AC、直接关联代码、
   复核轮次和证据范围照旧；全局轨道、Gate-echo、blocks/releases 检查仍扫描
   完整来源，不能只按当前工作项过滤。修改前仍重读待改章节并按最新磁盘内容
   合并；内容压缩执行 chore 细则的逐条核对，更新状态板后运行 `check_docs.py`。

## 7. 并发与冲突规则

0. **执行轨道纪律**：Active handoffs 分两路（`Lane` 列，闭集
   `fast`/`vlm`，归路判据见 `AGENTS.md`「执行轨道纪律」），每路任何时刻
   至多 **1 条消耗性活跃交接 + 2 条零消耗活跃交接**（消耗性 = 创建/消耗
   scenario/session/run ID、Play 配额或 API 预算，交接表 `Consuming`
   列声明）；其余一律 `PAUSED_<原因>`。强制核对由 **Gate-echo** 机检
   承担：每行交接内引用的、在 Gate board 有行的反引号标识（work ID 与
   `M1` 类里程碑行；判据 = token 表成员资格）必须以
   `` `<ID>`@<Overall> `` 形式逐字携带 Gate board 当前
   Overall token，不一致或超限即拒绝提交。
   暂停不改变已有 verdict 与证据，只冻结推进；发现失效交接文字仍须
   在同一批次就地修正。细则见 `AGENTS.md`"执行轨道纪律"，
   `tools/check_docs.py` 机械强制。
   本条在研究轨道与工程轨道上逐字相同：每路 1 条消耗性 +
   2 条零消耗的上限、Gate-echo 与 `PAUSED_*` 表示法都不因工程轨道
   放宽；Play/采集操作单沿用的共享槽位互斥使用约定按现状保留，不另立
   条文。工程轨道另按任务合同附一份预算信封，该信封由用户
   批准并逐字记入 `docs/authorizations.md`（无账本条目即视为未授权）；信封内
   的工程性重试不需要重复授权，超出信封的任何消耗——新 scenario/session/run
   ID、Play、正式数据 attempt、模型下载、模型 API、训练 GPU·h、公开发布——
   一律回用户；已无待执行动作的记录离开 Active
   handoffs，预算与锁的保护不删除。
1. 所有 Agent 的开工读取与修改前重读均按 §6.1 执行：开工读当前结构节与
   本项相关的 Gate board 行，修改前重读待改章节；不要求全文重读。
2. 跨多轮任务先在 Active handoffs 声明文件范围和状态。
3. 两个 Agent 不同时修改同一实现文件；复核角色只在一次性 worktree 中
   接触实现代码，主工作树保持只读。
4. 更新滚动日志时基于磁盘最新内容合并，不从旧上下文整文件覆盖。
5. 同时出现代码复核失败和 Unity 失败时分别保留，两者都交给接受角色
   归因。
6. Git 历史（若存在）负责版本追踪；Markdown 记录的是语义状态和验证证据，
   不能代替版本控制。
7. 每个角色收工提交前运行
   `python3 tools/check_role_writes.py --role <role>`，按 `docs/roles/`
   的写入白名单核对本批次**未提交**改动；报出越权路径时先恢复再提交。
   已提交批次的写入归因不做机械检查。工作流基础设施（`AGENTS.md`、
   `CLAUDE.md`、`docs/collaboration-workflow.md`、
   `docs/engineering-workflow.md`、`.claude/`、`.cursor/`、`docs/roles/`、
   `tools/check_*.py`、`tools/githooks/`）对所有角色只读，仅用户直接
   授权的协调批次可修改。**唯一例外（复核角色除外）**：
   非复核角色可在只改 `tools/check_*.py` 与 `tests/test_check_*.py` 的
   单独提交里修复自检工具的假阴性或坏夹具，提交信息必须贴出触发的失败
   输出，不得与证据产出混在同一提交，用 `python3

   diff。复核角色不适用本例外——红线 A 的五路径绝对禁令优先，复核
   发现自检工具缺陷时唯一合法动作仍是写复核文件。协调批次不运行角色写入
   检查（任何 role 选项都无法让 infra 改动合规通过，这是设计使然），

   启用前仍为用户直接指挥的协调会话。
