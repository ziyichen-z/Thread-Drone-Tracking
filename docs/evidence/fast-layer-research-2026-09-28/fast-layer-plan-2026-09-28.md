# 快层配合方案备忘：接口 A 下的「保持居中 → 换目标迁移 → Jetson」

- 日期 2026-09-28。性质：方向建议，不是提案、不是授权；仓库零改动。
- 依据：三份只读调研，A1 仓库事实核查（191 行）、A2 外部成熟方案（188 行）、A3 Jetson 可行性（212 行），均在本会话暂存目录 `scratchpad/research/`，已随本文发给你；暂存目录会随会话消失，要留存请自行指定位置。
- 数字标注：[仓库] = A1 从代码/证据核实；[公开] = A2/A3 的公开资料（URL 在原文件）；[估计] = 推算。

## 0. 一页结论

1. **快层改成「指针式」。** 检测器 + 多目标关联从会话开始常驻逐帧跑，对画面内所有车维护 track ID 和按 frame_id 的轨迹历史；被跟目标只是一个指向某个 ID 的指针。换目标 = 改指针，不再对单目标跟踪器做 init。det-assoc-v1 内部已经在做全画面关联，只是不外露 [仓库]。这一步顺带消掉 LOOP-001 卡住的 catchup_stale 根因：播种后回放几十帧积压再过单批发布门 [仓库]。
2. **VLM 的框（带 frame_id = k）用三级解析接到活目标上。** ① 在 k 帧的轨迹历史里同帧 IoU 匹配拿到 ID，沿 ID 走到当前帧；② k 帧上没有轨迹过门，就用冻结的 nanotrack-v2 在 k 帧起跟、回放缓存帧追平，再由检测轨迹「收养」；③ 命中的轨迹已经死了，就把 k 帧的框换算成世界点，转向后在误差区内重捕。三级分别对应乱序量测回溯、Sightline 的历史帧起跟、slew-to-cue，都是成熟做法 [公开]。
3. **转向要保住指针，必须做相机自运动补偿。** 现在 BoT-SORT 靠图像稀疏光流估计相机运动。未补偿时 5 Hz 下云台只能以约 5–15°/s 转才不断关联，而 Unity 云台是 120°/s，每帧最多 24°、约 185 px [仓库][估计]。帧元数据里有采集时刻的精确相机位姿 [仓库]，用它算纯旋转单应替换光流，转向期间关联可以不断。这同时是 Jetson 上省 CPU 的做法 [公开]。
4. **时延按 4–13 s 设计，不是 1.5 s。** 闭环选定宿主实测 VLM p50 4.2 s、p95 5.4 s、max 7.2 s；加人工确认后指定到首次写桥 8–13 s [仓库]。轨迹历史深度取 ≥ 20 s（盘上保留 128 帧 = 25.6 s，够）。对静止车：指定期间相机不动（现状），同帧匹配大多能成。对运动红车：5–13 s 内走 10–26 m，多半已出画或换了 ID，要靠③的世界点加速度外推重捕。
5. **验证目标换成「发现目标 → 跟上」。** 离线先出两条曲线：陈旧指定解析成功率随延迟、转向存活率（位姿补偿对光流补偿），零训练零 Play；再用一次 Unity 诊断 Play 量捕获时间与成功率。不设资格门，数字只描述。
6. **Jetson：快层上板没有算力问题；用户 09-28 裁定 VLM 也上板。** 板上 2B INT4 与快层共驻只在 headless 下成立，余量 0.2–2 GB；Jetson 探测可作为零 Play 独立项提前并行，先做 A3 协议第 0–5 步。
7. **动工前有八个决定要你拍板（§5）**，其中定局 ④/⑥/③ 的窄修订和 LOOP-001 的处置最关键，不裁定提案会在接受环节被退。

## 2. 架构：指针式快层

### 2.1 层 1：底座常驻 + 居中伺服（最基础）

- **常驻关联**：会话一开始就逐帧跑检测 + BoT-SORT，与是否有绑定无关；输出全部 track 并把每帧 `{frame_id: [track_id, box, score, cls, state]}` 存进 ≥ 100 帧的环形历史。改动集中在 det-assoc-tracker 的 `_step/update`（去掉「无绑定直接返回」）和会话的帧处理入口（去掉「无段不处理」）[仓库]。
- **位姿单应补偿**：用相邻帧元数据的相机姿态差算 H = K·R_Δ·K⁻¹，在关联前把所有轨迹的预测框映射到当前帧。ultralytics 8.4.104 的 `_pre_first_associate` 钩子接受一个 2×3 warp，可注入外部矩阵 [仓库]；纯旋转与景深无关，机身平移在 25 m 高度、目标 40 m 外的视差每帧约 12 px 量级，可先忽略 [估计]。图像光流保留为交叉校验。
- **指针语义**：`follow(track_id)`；对外观测只发指针指向的 track，`tracking_observation.json` schema v1 不用改 [仓库]。指针 track 在 buffer 内 unmatched 时报 coasting，被移除时报 `TRACK_ENDED`，都进闭集，不再是「只报 lost」。
- **居中伺服**：现在只在批末帧对「框底中点 ∩ 地平面」发 look_at [仓库]。v1 改成：每个处理帧都发、按指针 track 的卡尔曼预测提前半拍，并对云台步进限速；像素残差修正作可选项。静止车的 look_at 点稳定，居中在 1 s 内完成；运动红车靠预测前馈。机身沿用阈值规划器。
- **track_buffer 按秒定义**：5 Hz 下 30 次 = 6 s 偏长，行业取值 1–1.5 s [公开]；但 buffer 越短③越常触发。v1 保持 6 s，E2 实验里扫 2/4/6 s。

### 2.2 层 2：指定解析器与闭集

输入：VLM 结果包已经带 `frame_id`、`frame_sha256` 和框 [仓库]，接口 A 形态现成。解析器 `designate(box, k)`：

| 结果 | 条件 | 动作 | 对应成熟做法 |
|---|---|---|---|
| `BOUND` | k 帧历史里有轨迹与框 IoU ≥ τ 且次佳裕度 ≥ m，该轨迹现存活 | 改指针；连续伺服置中 | 乱序量测回溯；Sightline nearVal |
| `BOUND_COASTING` | 命中轨迹在 lost 池（buffer 内） | 改指针，等库自行找回；超时转 `TRACK_ENDED` | 同上 |
| `TRACK_ENDED` | 命中轨迹已被移除 | 用 k 帧位姿 + 框算世界点（运动目标加轨迹末速度 × 经过时间外推）→ 转向 → 误差区内 N-of-M 收养 → `BOUND` 或 `ACQUIRE_FAILED` | slew-to-cue；tf2 时间旅行 |
| `NO_TRACK_AT_K` | k 帧无轨迹过门（漏检或类别外） | nanotrack-v2 在 k 帧图像上 init，回放缓存帧到当前；被检测轨迹收养后 `BOUND`，否则 `SOT_UNCONFIRMED` 交人 | Sightline Precision Acquisition；仓库 reanchor 的 FrameHistory + replay_tracker 模式可复用 |
| `AMBIGUOUS` | ≥ 2 条轨迹过门、裕度不足 | 不改指针；走现有候选确认界面 | DJI WAITING_FOR_CONFIRMATION |
| `FRAME_NOT_IN_HISTORY` | k 超出历史 | 拒绝，重新查询 | Sightline Max Pause |
| `VLM_NONE` / `VLM_MULTI` | VLM 自报 | 上报操作者，不动作 | 现有三态 |

- τ 与 m 用 C2 的框质量标定：IoU 中位 0.86、≥ 0.5 占 87% [仓库]，起点 τ = 0.5、m = 0.2，并加「轨迹框中心落在 VLM 框内」的备用判据处理偏松框。
- 「把旧框按相机运动平移后在当前帧 init SOT」不可取：4–13 s 内运动目标走 2–7 个车长 [估计]，所以②必须在 k 帧起跟再回放。NanoTrack 的 update 恒返回成功，回放结果必须被检测轨迹收养才算数 [公开]。
- 静止车与运动车的预期不同：指定期间相机不动，静止车走①的比例应很高；运动红车 5–13 s 内多半出画或换 ID，③会是常态。E1 实验就是量这两个比例。

### 2.3 层 2：转向捕获与安全语义（进阶）

- **连续伺服（B 仍在画内）**：改指针后，现有「观测 → look_at」路径下一帧就把云台转向 B，不需要新指令 [仓库]；位姿补偿保证转向中关联不断；对 look_at 做步进限速，v1 起点 30°/s 并在 D1 里扫。
- **look-then-move（B 已出画或需机身动作）**：按世界点发 look_at；机身由阈值规划器在云台饱和后沿相机方位走，走满 24.5 m 约 6–7 s [估计]。这需要一条**无同帧观测的转向通道**：现发布门会把它判 orphan_control 并终止段 [仓库]。通道的安全语义：每次指定至多一次、时限 3 s、到位判据 = 云台角速率低于阈值且预测投影连续 N 帧在画内、失败回 hold 并报 `ACQUIRE_FAILED`。
- **状态机**：允许在 TRACKING 下 ask/respecify（现被拒 [仓库]）；捕获态 `SLEWING → ACQUIRING(N-of-M) → CENTERED`，另有 `COASTING`、`LOST(原因)`；丢失后仍走 SUSPECTED / 人工路径，不自动重播种。
- **可达性是硬边界**：默认锚点 36 m 内只有 4 辆静止车可居中、49.5 m 内 6 辆 [估计]。v1 演示的候选池就是这 4–6 辆加运动红车；要更大的池得改锚点或路线，那是配置不是 Unity 代码。
- **远小目标**：瓶颈更可能在 VLM 侧（32 px/token，65 m 外车宽约 15 px，半个 token）[公开]；检测器远目标召回 0.904 已够用。不做 SAHI；慢层内「粗定位后裁剪放大再问」作后续选项；是否允许相机变焦要你裁定。

### 2.4 层 3：Jetson（用户 09-28 裁定：VLM 也上板）

- **YOLO 的账**：算力几乎不占。TRT FP16 引擎 4.5 ms/帧，5 Hz 下 GPU 占空比约 2%，端到端约 16 ms [公开]。占的是内存：引擎本身 8 MB，但 CUDA/TensorRT 库常驻加 torch 约 0.5–1.5 GB；快层改用 TensorRT Python + numpy 关联器、不装 torch，可省 0.5–1 GB [估计]。
- **共驻预算（8 GB 统一内存，Linux 可见约 7.4 GiB）**：headless 系统 0.6–1.2 GB + 快层 0.5–1.5 GB + 2B INT4 4.3–4.5 GB（TRT Edge-LLM，KV 按约 1024 上下文收紧）= 5.4–7.2 GB，余量 0.2–2 GB；登录桌面再加 1.6 GB 就超 [公开][估计]。硬条件：headless、常驻不唤醒（唤醒式加载触发内存回收会让快层卡数秒）、4B / vLLM / bf16 都不与快层共驻。
- **GPU 争用**：VLM 只在指定时跑，每次约 1–1.5 s 解码占满显存带宽；检测器 4.5 ms 的核会被时间片穿插，预计单帧时延升到 2–3 倍仍在 50 ms 内 [估计]；指针式快层容得下几帧变慢。A3 协议第 5 步实测这一项，通过线：快层 p95 ≤ 单测的 2 倍且 ≤ 100 ms、峰值 RAM ≤ 7.0 GiB、无 OOM、swap 为 0。
- **VLM 运行时两条路**：(a) TensorRT Edge-LLM INT4 AWQ + FP16 ViT，JP7.2 官方支持并有同板数字（ViT 141 ms、prefill 167 ms/292 tok、36 tok/s、峰值 4.5 GB），单次指定估 0.95–1.45 s，比现在闭环宿主的 4.2 s 快；代价是 AWQ 量化要 x86 Linux GPU 主机（5060 是 Windows，WSL2 未验证，租云 1 小时即可），LoRA 先合并，板上源码编译建引擎。(b) llama.cpp Q4_K_M + mmproj：GGUF 转换与量化在 Mac 上 CPU 就能做，smoke-pack 里已有脚本；但 JP7.2 上图像路径未见公开验证、Tegra VMM 的多模态 OOM issue 未关、新图 TTFT 曾测到 2.3 s。建议 (b) 先冒烟，(a) 为正式路径。
- **量化后必须重跑 609 行**：看表 G 各组相对 bf16 C2 的差值与三态混淆（给框 / none / 歧义）；INT4 对框定位与三态的影响没有任何公开数据。这一步在 Mac 或桌面跑，不占板子。
- **快层上板细节**：TRT FP16、480×640 矩形导出省约 25%、不做 INT8；GMC 换位姿单应正好省下 CPU 光流；上板后把帧率提到 15–30 Hz 并对齐时间戳。
- **上板第一步**：`sudo nvpmodel -q` 核验 MAXN_SUPER 与 GPU 1020 MHz，JP7.2 镜像常装成非 Super [公开]。
- 按设计 §8 与 COORD-010 独立立项，写明设备与额度（下载 GGUF 约 1.9 GB 或 base 4.3 GB、量化主机时长或云费）；A3 §6 七步协议按 0 → 1 → 2 → 3 → 4 → 5 走，第 6 步改为下面的桌面机 ↔ Jetson 桥接测试。桌面机跑 VLM 降为断链 / 内存不够时的备选。

### 2.5 拓扑：Unity 留在桌面机，Jetson 当机载计算机（用户 09-28 明确）

- **分工**：桌面机只跑 Unity（相机帧、云台与机身 plant、CoverageEvaluator 与 metrics.json）；Jetson 跑检测 + 关联、指针与解析器、云台/机身决策、VLM，即整个 Python 控制器。Unity 跑不了 aarch64，本来也没有上板的选项。
- **桥接方式**：Unity 侧的文件桥零改动、控制器侧的文件语义零改动，中间加一个双向中继：桌面机上一个进程盯 `runtime/frames/latest.json`，把帧包（jpg + json）推到 Jetson 的镜像 `runtime/`，到达后原子写入；Jetson 上一个进程把 `tracking_observation.json`、`gimbal_command.json`、`body_command.json` 和语言桥的结果文件推回桌面机，同样原子写入；操作者请求文件走同一条通道反向。约两百行 Python。先用有线以太网直连，不走 Wi-Fi 或 Tailscale。
- **带宽与时延**：640×480 JPEG q85 约 30–80 KB/帧，5 Hz 约 0.2–0.4 MB/s，20 Hz 约 1–1.6 MB/s，千兆网可忽略；单向多一次 LAN 往返加文件落盘约 5–20 ms，对 200 ms 帧周期可忽略，对 50 ms 周期也够 [估计]。
- **时间基准是 K1 要写清的点**：现发布门用「采集墙钟年龄 ≤ T_stall」[仓库]，跨机后两台机器的时钟不同。做法：新鲜度门以 frame_id 差为主（现已有 K_pub），墙钟改用中继到达时刻相对年龄；两机用 chrony 对时只为日志对齐。
- **共享目录（NFS/SMB）作为快速替代**：零代码，但原子 rename 的可见性与属性缓存会破坏「原子发布」与 T_pub 计时，只适合冒烟，不适合闭环。
- **验证分两步**：D1 先在桌面机跑指针式快层（分离算法与部署），D2 用同一剧本把控制器搬到 Jetson 硬件在环再跑一次；A3 第 6 步改成中继测试：帧到达抖动、命令回程时延、断链时快层与 Unity 的行为。

## 3. 验证目标（替换保持率门）

### 3.1 离线 E1 / E2（零训练、零 Play、零新检测推理）

原料全在：主树 `outputs/eng-det/dets/` 有冻结检测缓存（B: scout-1 768 帧 + arm A 7×128；V: a7 3,168 帧；H 16,855 帧）；数据根有逐帧位姿 sidecar、S3 逐对象 object_id 与可见框、仿真时间；关联回放函数现成（`tools/eng_fast/replay.run_sequence`、`tools/eng_det/evaluate.replay_piece`）[仓库]。缺的只有 `lap` 在主树 venv 里没有，按 FAST-002 先例用数据根解释器。

- **E1 陈旧指定解析成功率随延迟**：在 scout-1、arm A、a7 上常驻回放 BoT-SORT 一次，记全帧轨迹历史。对每个 (k, object_id) 且该对象在 k 帧 OK 可见，构造指定框：干净版 = 真值框；VLM 版 = 按 C2 相对金标的 IoU 分布扰动。延迟 Δ ∈ {1, 2, 4.2, 5.4, 8, 13} s，在 k+Δ 解析，记七类结果；成功 = 指针 track 在 k+Δ 的框与同一 object_id 真值 IoU ≥ 0.3；对象在 k+Δ 已不可见则单独计「正确报告不可见」。分静止车 / 运动红车、S/M/L、位姿补偿 / 光流补偿四维出表。另用 609 行里 k+Δ 仍可见的 64 行真实 C2 框描述性对照。
- **E2 转向存活率**：a7 有每帧最大 22°、p90 8° 的扫视旋转 [仓库]，是转向压力测试。比较三种关联：光流 GMC、位姿单应、无补偿，出 13 s 保持率与 ID 切换数；顺带扫 track_buffer 2/4/6 s。
- 不用 H 域序列（FAST-002 已评一次，用则需声明）；scout-1、arm A 在训练原子内，对检测偏乐观但 E1/E2 量的是关联与解析，影响小，报告标注。
- 产出：两组曲线与一张七类结果分布表，无门值。这一个实验回答本方案最大的不确定点：指针在「延迟 + 转向」叠加下能不能保住。

### 3.2 Unity 诊断 D1（实现后，1 次 Play，≤ 3 min）

- 剧本：跟运动红车 → 人从检测候选里选静止车 B（不得用真值投影框 [仓库]）→ 量指定到绑定、到居中的时间与成败 → 切 C → 切回红车。覆盖除「切到另一辆运动车」外的全部环节，Unity 场景零改动。
- 评估：Unity 评估器只认 target-0 [仓库]，静止车 B/C 的成败要靠归档帧离线复算（`tools/dist_data/project_boxes.py` 可对任何归档 Play 帧算框）或人工目检；先把 `retained_frame_count` 从 128 调大以留住整段帧（配置项，不是代码）。

### 3.3 指标定义与坑

- 捕获成功率：指令后 T_max 内指针绑定真目标且目标中心距画面中心 < r 连续 N 帧；按指令时刻目标偏轴角（画内 / 出画但 45° 内 / 需机身）与斜距分桶。
- time-to-bind、time-to-center：含 VLM 延迟，报 T 内成功率曲线，不只对成功样本统计。
- 误锁率：绑到非目标车的比例与时长。
- 分段归因：VLM 框对不对 → 解析 ID 对不对 → 转向到没到 → 捕获后丢没丢。
- 坑：离线评测忽略延迟（PVT++ 报告在线最多掉 70%）[公开]；捕获定义事后才定；每桶样本太少。
