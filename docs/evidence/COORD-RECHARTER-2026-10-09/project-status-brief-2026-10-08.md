# 系留无人机「语言指定跟踪」项目：现状、实测与疑点（2026-10-08）

## 0. 一句话

Unity 仿真里的系留无人机，用一个 2B 小 VLM 按自然语言指定地面车辆，快层跟踪并让云台和机身保持居中，丢失时显式报告。当前闭环能跑通「指定 → 绑定 → 居中」，但目标一移动就跟不住，交互流程也不适合演示。我怀疑架构本身有缺陷，想换个脑子重新审视。

## 1. 目标与约束

- 目的：求职作品集的工程首版，不是论文。要有可复现的开源示例和一段能看的演示。
- 已锁定的主线文字（逐字）：「做一个闭环系统：语言指定目标，快层跟上并保持居中，换目标时能迁移并跟上新目标，丢失与歧义显式报告。VLM 是主角（接口 A：输出框 + 所在 frame_id）；快层是非变量，但必须能换目标。部署目标是 VLM 与快层跑在 Jetson Orin Nano 8GB（headless），Unity 留桌面机。项目的难点是『发现目标 → 跟上』，不是保持跟踪。验证只看四类数字：陈旧指定解析成功率随延迟、转向存活率、捕获时间与成功率按偏角/距离分桶、误锁率与显式报告比例。」
- 自设的不做清单：不做 ReID、不做 SAM 2 在线、不换更大模型、不做 INT8、不做 SAHI、不改 Unity 场景；不为快层做研究主张。
- 硬件：VLM 与快层跑在 Jetson Orin Nano 8GB Super；Unity 跑在 MacBook Air；两机经 SSH 相连。

## 2. 场景

Unity 城市街区。一辆红色轿车按固定路线以 2 m/s 绕圈，其他车全部静止。无人机悬停在 25 m 高，系留约束已于 2026-09-30 正式放弃，改用围栏、高度与速度边界，云台独立转动，离底最多 45°，转速 120°/s。相机以 5 Hz 输出 640×480 JPEG 加位姿元数据。Unity 与 Python 只通过一个目录里的 JSON 文件交换，真值只给离线评分，控制回路碰不到。

## 3. 现在的架构

### 3.1 慢层：VLM

- Qwen3-VL-2B-Instruct + LoRA r16。训练集 4,907 条图文对，闭集词表：九类车（car、suv、taxi、police car、ambulance、bus、truck、pickup truck、container truck）× 六种颜色。
- 输入一帧加一句指令，输出三态 JSON：unique 给一个框 / ambiguous 给多个候选 / none。
- 合并后转 GGUF Q4_K_M，用 llama-server 跑在 Jetson 上，温度 0。
- 609 行评估：单目标选框比零样本 +26.6 pp，格式零失败；但歧义 48 行里 29 行不报歧义直接挑一个；不存在 100 行里 21 行硬给框。功能门未过。

### 3.2 快层

- 域内微调 YOLO11，类别只有 vehicle / target（target 是把红车单独当了一类，属于场景专用捷径）。BoT-SORT 关联，无 ReID，丢失轨迹保留 30 次更新约 6 s。
- 常驻逐帧跑，画面里所有车都有轨迹 ID，128 帧历史按 frame_id 索引。
- 被跟目标只是一个指向轨迹 ID 的指针，设计上从不改绑。VLM 的框带着 frame_id k，在 k 帧历史里按 IoU 找到 ID，再沿 ID 走到当前帧。k 帧的轨迹已经死了，就用 k 帧位姿和框算世界点，云台转过去，连续几帧收养附近的新轨迹。

### 3.3 控制

- 指针框底中点与地平面求交得世界点，作为云台 look_at。
- 机身规划器按距离带出速度或 hold：目标距离 12 m，带宽 4 m，最大 4 m/s，命令 0.4 s 过期。
- 每次写桥都过五项发布门：帧身份、图像哈希、元数据、帧差不超过 2、时限。

### 3.4 操作流程（现状）

本机网页。按「发送」→ 会话取最新帧 N → VLM 回答 → 网页在帧 N 的截图上画框并倒计时 10 s → 操作者「确认」或「拒绝」→ 绑定指针。跟踪中丢失要等库删掉 ID 才报 SUSPECTED，由人 confirm_lost 或 respecify。另有低频 verify 让 VLM 复核当前框。

这套流程是为测量「四类数字」设计的，带延迟注入、意图标志、逐步受理，每步留证据。指令文字是 Play 前冻结在剧本里的，操作者只按发送。

## 4. 2026-10-08 实测：一次完整 Play，四次指定

| 指定 | 指令 | VLM 等待 | 人工确认等待 | 发送到绑定 |
|---|---|---|---|---|
| 1 | the suv | 1.9 s | 9.4 s | 11.4 s |
| 2 | the taxi | 2.0 s | 5.9 s | 7.9 s |
| 3 | the red car | 2.0 s | 2.7 s | 4.6 s |
| 4 | the suv | 2.0 s | 3.2 s | 5.2 s |

- 四次都返回 unique 并成功绑定。操作者评价交互顺畅。
- 第三次是唯一的移动目标，绑定后第 4 帧就丢了。机制已对照日志和代码确认：指针切换使 look_at 从 taxi 跳到红车，云台连续三帧各转 5.2° / 3.6° / 2.8°，5 Hz 下每帧约 40 像素的画面位移让 BoT-SORT 关联断掉，指针留在死 ID 上。此后 31 帧输出空框，不发云台命令，机身 hold，6 s 后库删 ID 才报 tracker_failure，红车 8 s 后驶出画面。丢失期间的原图里红车很大、无遮挡、在画面中部。
- 整场 158 s 机身只动过 0.7 m，居中全靠云台。机身会不会跟随，这次没测到。
- 另有三个工程问题：板端服务释放未确认、收尾工具挂起、手工 SIGTERM 偏差。

## 5. 我认为的缺陷

1. **交互模型。** 文本指定加人工确认，对可见目标比点击慢得多，且没有任何优势。真实操作者没时间敲字，也没时间看旧截图再确认。
2. **VLM 的位置。** 对画面里可见目标的首次指定，VLM 在速度和准确度上都输给「点击 + 检测器」。它真正不可替代的是：丢失后按描述找回同一辆、核验「跟的还是它吗」、目标不在画面时的语言指定。但现在的流程和评估都围绕首次指定设计，没有围绕这三件事。
3. **快层。** 指针从不改绑，一次 ID 切换就终结；丢失期间不滑行、不发云台命令；跟踪中丢失不触发重捕，只有陈旧指定才触发；相机位姿每帧已知却不用来做运动补偿，而是依赖稀疏光流，Unity 场景纹理很少。
4. **机身跟随未验证。** 规划器几乎全程 hold。
5. **VLM 的弱项正好是新角色最依赖的能力。** 歧义不报、不存在硬给框，对应到找回场景就是两辆红车时自信挑错、目标未到时误锁别的车。
6. **仿真天花板。** 闭集车模，同色同类的车描述上无法区分；检测器的 target 类是捷径，真实场景不存在。
7. **流程过重。** 多角色、授权信封、必经停点的研究式流程让一次诊断成本很高，最近三次诊断分别耗在 ssh 套接字路径、收尾挂起、手工信号上，功能缺陷反而是事后从盘上原件零成本定位的。

## 6. 目前在考虑的方向（不是定论）

- 演示模式与测量模式并存。演示模式：点击即绑定，快层直接从当前帧的框里挑；VLM 并行给闭集描述作为语义身份，不要确认步骤；丢失后按描述找回，经运动合理性检查后绑回；语言入口保留给画面外指定和接力。
- 快层：unmatched 时也走收养逻辑；滑行期用预测框继续发 look_at；用帧元数据的位姿做运动补偿；换目标时限制云台转速。
- 不重训 LoRA。先探针现有模型「框 → 闭集描述」的零样本能力，不行再把训练对反转做多任务 LoRA。
- 代价是主线文字要从「语言指定目标，VLM 是主角」改成「VLM 持有目标的语义身份，负责找回、核验与画面外指定」。

## 7. 想请你一起想的问题

1. 「VLM 是主角」在上述张力下还能不能成立？什么角色是 VLM 真正不可替代、而且在 Unity 闭集场景里能演示出来的？
2. 交互设计：点击、语言、混合，真实操作和演示各该怎么选？有没有我没想到的第四种？
3. 快层在不做 ReID 的前提下，有没有比「指针 + 收养」更稳的设计？位姿补偿和光流补偿怎么取舍？
4. 四类数字还是不是对的评估指标？如果换角色，该换成什么？
5. 闭集仿真对 VLM 故事的伤害有多大？值不值得打破「不改 Unity 场景」这条？
6. 一个人的作品集项目，严谨流程和推进速度该怎么平衡？现在的流程哪些该砍？
