# P1-SCENE-002 — 道路合法路线、放置时序不变量与随机路线设计立场

Created: 2026-07-27
Last updated: 2026-07-27（修订 2：逐项响应 Codex round 1 五项必改；

用户 2026-07-27 在修正后场景的 Unity 观察中反馈三项问题（对话反馈，
正式 `UT-P1-SCENE-001-001` 记录由 Codex 按角色分工代录）：

1. 进入 Play 时被重定位的车辆发生可见"瞬移"，并追问：将来目标随机
   移动时还这样瞬移吗？还是伪随机限定好路线、但不让 VLM 知道？
2. 现行路线有一部分让目标车开上了人行道。
3. 有时目标车与电线杆/路灯类杆件穿模（修订 1 并入）。

## Problem and research value

### 1.1 路线与道路网格的实测偏差（人行道缺陷）

对场景全部 117 个道路预制件实例的解析显示，目标路线所环绕街区由四条
道路中心线围成：北 z=120、南 z=60、西 x=120、东 x=180（20×20 m 路
瓦片，`Road Lane_01`/`Intersection` 系列）。现行 `route_world_m` 各
主段相对道路中心线的偏移：

| 路段 | 现行位置 | 道路中心线 | 偏移 | 判定（估） |
|---|---|---|---|---|
| 北段 | z=117 | z=120 | 3 m（街区侧） | 沥青内但贴路缘 |
| 东段 | x=183 | x=180 | 3 m（外侧） | 沥青内但贴路缘 |
| 南段 | z=63 | z=60 | 3 m（街区侧） | 沥青内但贴路缘 |
| **西段** | **x=129** | **x=120** | **9 m（街区侧）** | **越过路面，在人行道/街区边缘** |

路瓦片是单体网格（路面 + 人行道合并），沥青带精确宽度须由 Codex 在
编辑器内实测；但 9 m 偏移超出 20 m 瓦片的任何合理沥青半宽，西段
"开上人行道"与用户观察一致，属确定缺陷。其余三段贴路缘行驶也解释了
P1-SCENE-001 发现的三处停车剐蹭为何全部出现在 0.15–0.85 m 距离上：
路线本来就压着路边停车带画。

连带问题：P1-SCENE-001 的三个重定位落点（出租车 z=112.5、卡车
(168.25, 110.5)、警车 (190, 89.07)）按同一网格判断很可能落在人行道
带上——这正是该提案开放问题 1 与 Sonnet 复核注记 2 明确留给用户
Unity 目检的项，现在应与路线一起按道路语义统一修正。

### 1.1a 街道家具穿模与审计覆盖缺口（修订 1）

用户随后反馈目标车有时与电线杆/路灯穿模。对场景 584 个地面
props/natures 实例的同法解析显示，距**现行**路线中心线 2.5 m 内有
9 个道具，**全部在西段**（即人行道段）：

| 道具 | 距中心线 | 位置 |
|---|---|---|
| 小广告牌 ×4 | 0.63 m | x≈128.4, z∈{71.4, 81.8, 92.4, 103.7} |
| 消防栓 | 1.26 m | (127.7, 68.7) |
| 大型红绿灯杆 ×2 | 1.40–1.42 m | (127.6, 67.6) / (127.6, 112.5) |
| 路灯 ×2 | 1.55 m | (127.4, 80.0) / (127.4, 100.0) |

按走廊准则（目标半宽 1.0 + 障碍半宽 + 裕量 0.5）九处预计全部违规。
杆件穿模与"西段在人行道上"同根因：人行道本来就是街道家具的所在。
对提案内环路线的同一检查显示 2.5 m 内道具数为 **0**——道路合法
路线自动消除该类冲突。

暴露的审计缺口：P1-SCENE-001 的走廊审计**只枚举 `Vehicle_*` 预制件**
（104 实例），街道家具、自然物与建筑不在扫描域内，同类冲突当前不可
机械检出。本项将审计泛化（§2.2a）。

### 1.2 "瞬移"的定性与放置时序不变量

被重定位车辆在进入 Play 的瞬间跳到新位置，是因为配置驱动的修正在
会话构建期（首帧发布前）一次性生效——发布出去的每一帧（包括第一帧）
都只包含修正后的世界，测量数据里不存在任何可观察的移动，编辑器里
看到的"瞬移"是 edit-mode 场景与构建后会话的差异，属外观现象而非
测量缺陷。但该语义目前只是实现事实，未被写成可测试的设计不变量。
本项将其显式化：**评估域内的任何 actor（目标、干扰车、被修正车辆）
的放置只允许发生在会话构建期、首帧发布之前；测量会话进行中不得有
任何非运动学的重定位，违反即 fail-closed。**

### 1.3 未来随机移动的设计立场（回答用户提问）

用户问"目标随机移动还要瞬移吗？还是伪随机限定路线但不让 VLM 知道"。
设计立场（本项落文字，不落实现）：

- **伪随机 = 种子冻结的路线生成**：M5 场景随机化用带种子的路线
  生成器在道路图上生成路线，会话创建时冻结并纳入配置哈希链——同一
  种子可复现，审计可追溯；
- **感知端不知情是既有硬边界的直接推论**：Unity 真值只允许进入
  `CoverageEvaluator`；路线/航点属于真值，本来就永远不进入追踪器、
  VLM 或任何传感器元数据，感知端只看到渲染帧；
- **瞬移只存在于会话出生时刻**：随机化改变的是"会话构建时的布局"，
  与今天的重定位一样发生在首帧之前，测量期间永不瞬移；运动中的
  目标与未来的移动干扰车都只做运动学连续移动；
- 每条生成路线必须通过与手工路线**完全相同**的道路合法性审计与
  走廊净空审计（§2.2），不合法即弃并按种子顺序重采。

### 1.4 研究价值与时机

道路合法路线是"场景难点受控设计"的底线：目标在人行道上行驶会让
遮挡结构、干扰车关系和论文可信度全部失真。时机上 B1 战役已
fail-closed 归档、B2 尚未创建、`UT-P1-SCENE-001-001` 尚未通过——
现在改路线不作废任何冻结工件，且能把 SCENE-001 与本项合并为
**一次**重冻结和**一次**用户全环验证。

## Proposed behavior

### 2.1 道路合法内环路线（修订 2：车道语义冻结）

以"道路中心线 − 车道偏移"重画四条主段。**车道语义冻结为顺时针
环行、靠右行驶**（必改 4；用户若需其他行驶语义，须在接受前提出，
接受后随提案一同冻结）：

- 北段 z≈117.5（东行），东段 x≈177.5（南行），南段 z≈62.5（西行），
  西段 x≈122.5（北行）；保留斜切角；周长约 213 m。以上数字**仅为
  规划参考**：车道偏移与斜切角的正式数值只能来自 Unity 内沥青
  边界实测（§2.2b 道路数据），禁止目测手调或沿用估计值。
- 四段偏移必须一致（同一车道语义），不允许逐段手调。

### 2.2 路线—道路合法性审计（扩展既有场景合法性门）

- Codex 在编辑器内实测路瓦片沥青带（方法与数值入证据文档），生成
  版本化道路图数据（瓦片中心/朝向/沥青半宽）；
- `RouteCorridorAuditor` 增加路线合法性检查：沿路线 0.5 m 采样，
  每个采样点的 XZ 必须落在某路瓦片的沥青带内；采样必须完整覆盖
  直线段、斜切转角与路口衔接（`Intersection`/`T_Intersection` 瓦片
  过渡处，必改 4）；与走廊审计同点执行、同样 fail-closed；
- **可证伪再现**：对现行路线，该审计必须至少把西段整段标为违规
  （其余三段按实测沥青带判定）；对修正路线报告 0 违规。

### 2.2a 三维车辆扫掠包络审计（修订 2 重写，响应必改 1）

**判据**：目标扫掠包络 = 路线走廊（水平半宽 `target_half_width +
clearance_margin`）× 高度区间 `[0, target_height_m +
vertical_clearance_margin_m]`（目标 renderer 实测总高约 1.55 m；
两个裕量均为配置项）。障碍物只有在**水平净空与目标高度区间同时
相交**时记违规——纯 XZ 投影重合不构成违规。

**确定分类规则**（每个激活 `MeshRenderer` 恰好落入一类）：

1. `road-surface`：canonical 名匹配道路数据允许列表（`Road *`
   瓦片与所列路面标线）→ 豁免；
2. `runtime-actor`：评估域运行时 actor（目标、无人机、锚点视觉、
   系绳）→ 豁免；
3. `overhead`：地面足迹（见下）与走廊不相交，且其包围盒与走廊
   相交部分的最低点高于包络顶 → 不违规（红绿灯横臂、招牌悬臂、
   雨棚等合法架空结构）；
4. `ground-obstacle`：其余全部（杆柱、树干、广告牌、消防栓、
   长椅、建筑边缘、车辆）→ 按判据审计，报告按
   vehicle/prop/nature/building/other 分组计数。

**L 形道具的地面足迹**：单体网格（如带横臂的红绿灯）的 3D AABB
同时覆盖杆柱与横臂，纯 AABB 判定会把合法横臂当作地面障碍。Edit
Mode 生成器按"顶点 y < 包络顶"过滤三角形，为每个预制件预计算
**局部系地面足迹 XZ 范围**写入道路数据（§2.2b）；运行时审计用
实例 TRS 变换该足迹判定，不在运行时读取网格。道路数据缺少某
在场预制件的足迹条目时 fail-closed。

**直接回归用例**（最少集合）：

- 走廊内路灯/红绿灯**杆柱** → 违规（杆件必检出）；
- 横臂跨越走廊上方、杆柱在走廊外的红绿灯 → 不违规（架空豁免）；
- 走廊内广告牌、消防栓、树干 → 违规；
- 走廊内 `Road *` 路面瓦片 → 豁免。

该审计同样约束 §2.3 的重定位落点与未来 M5 随机路线的合法性检查。

### 2.2b 道路数据的版本化与运行时绑定（修订 2 新增，响应必改 2）

- 单一入库文件 `config/road_data.json`（名字可由 Codex 定）：
  `schema_version`、路瓦片中心/朝向/实测沥青半宽、路面允许列表、
  各预制件局部系地面足迹、显式分类覆盖条目；由 Edit Mode 生成器
  产出、入库评审，实测方法与原始读数入证据文档；
- 三份入库 scenario config 各自携带该文件内容的 SHA-256
  （`road_data_sha256`）；会话构建时按固定路径加载并校验：文件
  缺失、哈希不符、schema 未知、条目重复、足迹缺失、分类未知，
  一律 fail-closed 终止构建，无容错回退；
- 三份配置必须引用**同一**哈希；道路数据任何变更都会改变三份
  配置的哈希，自动进入既有 config SHA-256 冻结链——同一配置哈希
  在不同道路数据下得出不同合法性结论的情形被结构性排除（Codex
  rationale 第 3 条）；
- 代码中不得散落隐式路径或别名字符串；路径常量唯一。

### 2.3 重定位落点按道路语义重指

- 三辆车改停道路合法位置（路缘停车带或合法泊位）：出租车必须留在
  20 Hz 标定帧脚印（x∈[112.6,151.4], z∈[102.5,131.6]）内且满足对
  **新**路线的走廊净空——候选如北路对侧停车带 (≈138.9, 122.5~123.5)；
  卡车、警车移至各自街道的合法路缘；
- **教训并入（修订 2）**：`UT-P1-SCENE-001-001` 目检发现 SCENE-001
  的出租车落点 (138.9, 112.5) 与一盏路灯重叠——重定位落点自身就是
  障碍物审计的对象。所有落点在提交稳定候选前必须通过 §2.2a 泛化
  审计（以停放车辆为"目标"的静态净空检查）+ §2.2b 道路数据复核，
  上述坐标仅为候选；
- 视觉合理性仍归用户 Unity 目检。

### 2.4 放置时序：结构不变量与验证诊断分责（修订 2 重写，响应必改 3）

**结构不变量（正式与验证会话恒成立，不依赖任何监视器）**：

- bootstrap 在首个发布帧之前完成全部评估域放置（既有构建顺序），
  由直接测试锁定：构建完成时刻与首个发布帧时刻的目标/被修正车辆
  位置逐一相等；
- 第一方放置 API（`PlaceAtRouteDistance`、场景修正应用）加**阶段
  守卫**：会话进入测量阶段后（RATE 会话释放帧之后；普通会话首帧
  发布之后）再调用即抛异常，fail-closed，守卫路径有直接测试。
  测量期重定位由此被结构性阻止，而非事后检测。

**验证诊断（仅验证会话显式启用，默认关闭）**：

- 逐帧跳变检测只作为发现**未知**移动路径的证据工具：位移阈值
  `> 2 × configured_speed × deltaTime`（航点停顿帧速度为 0，天然
  不触发），采样钟 = 仿真 deltaTime，触发时把帧号/位移写入独立
  JSON 证据工件，不终止会话、不写入 `CoverageEvaluator`；
- **本修订不把"测量期跳变"定义为需运行时检测的正式协议违规**
  （必改 3 两分支中取"结构不变量"分支）：正式会话的保证来自
  结构守卫与测试，验证诊断不承担 fail-closed 责任，也不在正式
  会话启用；
- 合并 Unity 用例必须使用**显式启用诊断的验证配置**并在用例文档
  中写明配置文件与哈希——SCENE-001 动态项因默认配置未启用监视
  而无效的教训直接落为用例前置条件。

编辑器内 Play 起始的视觉跳变是治理选择（不改第三方场景文件）的
固有代价，作为已知外观现象写入文档；若未来需要演示级平滑，可
另行评估项目自有场景变体，本项不做。

### 2.5 显式非目标

- 不实现路线随机生成器（§1.3 只落设计立场，实现属 M5 独立提案）；
- 不引入物理/避让、不改指标公式、不改帧/控制协议与统计规则；
- 不改锚点物理位置与无人机/云台/传感器参数。

## Inputs, outputs, and affected interfaces

- 修改：三份入库 scenario config 的 `route_world_m` 与
  `scene_adjustments.vehicle_relocations` 数值；`RouteCorridorAuditor`
  增加道路合法性检查；道路图数据文件（新增，版本化）；

- 输出工件：沥青带实测记录、修正前后路线合法性与走廊审计报告

## Compatibility with the current v0.3 design

- B1 已归档、B2 未创建，改路线不作废任何现存冻结工件；B2 的
  scouting/标定在本项落地后一次性冻结（承接 SCENE-001 绑定澄清 5
  的 B2 命名与集成目标）；
- 反天花板要求保持：内环路线仍绕同一街区，建筑/树木遮挡结构不变，
  `C_geom` 显著 < 100% 作为验收观察项复查；
- 真值边界不变：道路图与审计只服务场景合法性与证据，不进入感知/
  控制/指标路径。

## Acceptance criteria

1. **审计再现缺陷（三维判据）**：对现行路线+实测沥青带，道路
   合法性审计至少标出西段违规；三维扫掠包络审计对现行路线至少
   报告 3 处车辆违规（SCENE-001 已知）加 §1.1a 街道家具中按地面
   足迹判定成立的违规（预计 9 处，最低含 4 块广告牌与杆柱类）；
   §2.2a 的四组分类回归用例全部通过（含"横臂跨走廊上方不违规"
   的架空豁免反例）；对修正路线与全部新落点报告 0 违规，数值与
   独立几何计算一致（±0.1 m）。
2. **道路数据实测与绑定有测试**：测量方法、原始读数、导出车道
   偏移与 `road_data.json` 一并入库可独立复核；文件缺失、哈希
   不符、schema 未知、条目重复、足迹缺失、分类未知六类失效各有
   fail-closed 直接测试；三份配置引用同一哈希由测试锁定。
3. **放置时序分责有测试**：构建值与首帧位置一致性测试通过；放置
   API 阶段守卫在测量阶段调用时抛异常（直接测试）；验证会话中
   跳变诊断对注入的人为跳变产出证据工件（直接测试），正式测量
   配置下该诊断保持关闭且无 fail-closed 责任。
4. **SCENE-001 既有门在新数值下全部保持**：配置严格性、唯一匹配、
   基数门、代理一致性、缺省配置字节不变等既有测试全绿。
5. **合并用户 Unity 验证与顺序门（必改 5）**：`UT-P1-SCENE-001-001`
   的目检 FAIL 永久保留；其未完成项并入新的 `UT-P1-SCENE-002-001`，
   该用例**仅在修订提案被接受、实现形成稳定候选并通过 Sonnet 复核
   后**执行，且必须使用显式启用跳变/相交诊断的验证配置（配置与
   哈希写入用例）。用例内容：目标全环行驶始终在路面上、全程不与
   任何车辆/杆件/街道家具相交（诊断计数 0）、被重定位车辆停放
   视觉合法、整环约 107 s、`C_geom` 反天花板保持。该用例通过前
   不得创建 B2 战役。

## Baselines and ablations

合法性修复，无算法消融。证据 = 修正前后审计报告对 + 沥青带实测
记录 + 合并 Unity 验证结论。

## Failure modes and resource risks

- **车道偏移估错**：若 2.5 m 不符合实测沥青带，贴缘问题重现——
  偏移只能由实测导出，审计兜底，禁止目测手调；
- **斜切角越界**：转角斜切可能切出沥青带，审计采样必须覆盖斜切段，
  违规则加大切角半径或改直角；
- **出租车落点约束冲突**：标定脚印 ∩ 新走廊净空 ∩ 合法停车带若为
  空集，回退方案是将出租车改停北路脚印内其他合法位并复核标定帧
  视野包含性，仍不满足则升级为决策区问题；
- **用户时间**：合并验证约一整环 + 目检，一次完成，避免 SCENE-001
  / SCENE-002 两轮重复验证；
- 纯桌面改动，无新依赖。

## Suggested implementation scope

建议（不强制）：config 数值修订 + 审计器扩展 + 道路图数据生成与
实测证据 + 时序不变量测试 + 合并 Unity 用例文档。今日用户对话反馈
由 Codex 代录进 `docs/unity-test-log.md`（`UT-P1-SCENE-001-001`
目检项按实际结果记 FAIL/BLOCKED，成因指向本项）。

## Open questions

修订 2 已关闭 round 1 的开放问题 1（车道语义冻结，§2.1，用户可在
接受前提出异议）、3（道路数据入 `config/` 并哈希绑定，§2.2b）、
4（合并门顺序按必改 5 落死，验收 5）、5（允许列表由道路数据显式
枚举并 fail-closed，§2.2a/§2.2b）。仍开放：

1. 斜切角数值来自沥青边界实测后的路口几何（保留 3 m 或加大），
   由 Codex 实测后定；
2. `vertical_clearance_margin_m` 的默认值（建议 0.5 m），由 Codex
   结合目标 renderer 实测总高定；
3. 非均匀缩放的预制件实例是否存在（若存在，地面足迹的 TRS 变换

## Codex review decision

Decision: REVISION_REQUESTED

Rationale:

- 用户已于 2026-07-27 明确授权把原本的车辆小修扩大为“重画道路路线
  + 扩展合法性审计”，因此范围确认门已解除。西段位于人行道、现行走廊
  内存在街道家具以及 SCENE-001 目检失败，足以证明路线级修复方向合理。
- 现稿仍不能直接实现：§2.2a 把全部 `MeshRenderer` 的 XZ 包围盒都当作
  地面障碍，会把有足够净高的交通灯横臂、雨棚等合法架空结构误判为
  冲突；“静态地面障碍物”的名称与实际二维扫描域不一致。
- 道路图和路面允许列表既参与运行时 fail-closed 判定，又声称不改变
  `ScenarioConfig`，但没有定义文件发现、版本、内容哈希和场景配置之间
  的绑定。未绑定的道路图会使同一 scenario/config 哈希在不同道路数据
  下产生不同合法性结论。
- §2.4 同时声称测量期非运动学跳变属于正式协议违规，又规定相关监视在
  正式测量配置关闭。关闭的验证诊断不能为正式会话提供 fail-closed
  保证，必须拆分“构建顺序不变量”和“可选验证诊断”的责任。

Required revisions:

1. 将全障碍审计改为明确的三维车辆扫掠包络判据：水平净空与目标车辆
   高度区间均相交时才算障碍。杆柱、树干、建筑边缘必须被检出；净高
   足够的交通灯横臂、招牌悬臂或雨棚不得仅因 XZ 投影重合而失败。给出
   ground/overhead/road-surface 的确定分类规则和直接回归用例。
2. 定义版本化道路图/允许列表的运行时绑定：scenario 配置必须携带其
   schema/version 与内容 SHA-256（或把数据直接嵌入已冻结配置），缺失、
   哈希不符、未知分类或重复条目均 fail-closed。三份入库配置必须引用
   同一已审道路数据；不得依赖代码中的隐式路径或散落字符串。
3. 重写放置时序条款：bootstrap 在首帧前完成放置是始终成立、可直接
   测试的结构不变量；验证会话的跳变监视只是诊断证据。若要把测量期
   跳变定义为正式协议违规，检测必须在正式会话保持启用，并明确位移/
   速度阈值、采样时钟、证据工件与误报处理，同时继续禁止写入
   `CoverageEvaluator`。
4. 修订稿明确冻结顺时针、靠右行驶的车道语义；精确车道偏移和斜切角
   只能来自 Unity 内沥青边界实测。道路合法性审计须覆盖直线、转角和
   路口连接，现行路线至少复现西段失败，候选路线必须为零违规。
5. 明确合并门：`UT-P1-SCENE-001-001` 的目检失败永久保留；其未完成
   项并入新的 `UT-P1-SCENE-002-001`，但仅在修订提案被接受、实现形成
   稳定候选并通过 Sonnet 后执行。该合并用例通过前不得创建 B2。

Accepted design-document changes:

- None. 正式设计保持 SCENE-001 已接受版本，等待修订稿复审。

## Codex review decision — Round 2

Decision: ACCEPTED

Rationale:

- 修订 2 逐项闭合 Round 1 五项必改：审计从二维投影改为带架空反例的
  三维扫掠包络；道路数据以单一文件和内容哈希绑定三份 scenario；
  首帧前放置由结构守卫保证、跳变监视降为验证诊断；顺时针靠右的车道
  语义冻结且精确数值推迟到 Unity 实测；SCENE-001 FAIL 与新 Unity 门
  的顺序也已写死。
- 用户已明确授权路线重画与审计扩展。B1 已归档、B2 尚未创建，因此
  现在修正路线不会使任何有效冻结战役失效，并能避免在已知非法路线
  上继续积累不可解释证据。
- 该设计保持主指标、帧/控制协议与真值边界不变；道路数据、合法性审计
  和验证诊断均不得进入 sensor、tracker、VLM、controller 或
  `CoverageEvaluator`。

Binding clarifications:

1. §“Inputs, outputs”中“不改 `ScenarioConfig` 解析结构”的表述被本
   决定覆盖。实现必须为 `road_data_sha256`、目标扫掠高度、垂直裕量
   和验证诊断开关增加版本化、严格校验的 scenario 字段；字段缺失、
   非有限或哈希格式无效均 fail-closed，不得依赖 `JsonUtility` 的静默
   缺省。
2. §2.2a 的垂直区间不得在实现中硬编码为世界坐标 `[0, ...]`。道路
   数据必须提供每个采样处的路面高度/平面，扫掠包络以该表面为下界，
   再叠加实测目标底部偏移、目标高度与垂直裕量。当前场景即使平坦也要
   通过该通用途径。
3. 预计算地面足迹必须对实例完整 TRS 有确定语义。非均匀缩放若未精确
   支持，则生成器或运行时必须在稳定候选前 fail-closed；不得把它留作
   静默近似。`road_data.json` 的 SHA-256 绑定精确文件字节。
4. 跳变诊断阈值须以本帧允许的运动学位移加有限 epsilon 判定，避免
   零速/停顿帧因浮点噪声误报。它只写独立验证工件；正式保证仍来自
   放置 API 阶段守卫，不进入 `CoverageEvaluator`。
5. 实现属于改变正式路线语义的独立 work item：形成稳定候选并完成
   自动证据后必须提交、推送、交 Sonnet 独立复核并停止。只有 Sonnet
   通过后才运行 `UT-P1-SCENE-002-001`；该用例通过前不得创建 B2。

Accepted design-document changes:

- `docs/phase1-single-drone-design.md` 新增 P1-SCENE-002 道路合法路线、
  哈希绑定三维净空审计、放置时序分责与合并 Unity 门。
