## 2. 应该怎么优化

原则：**新会话接手当前工作需要的内容留在状态板；其余移走但不删除。**
"不影响当前工作"落成一条可机检的验收：本批 diff 不改动任何含 `P1-ENG-LOOP-001` 的行（§6-2）。

### O1｜非活跃项整段移入 `docs/parked-status.md`

- 新文件 `docs/parked-status.md`（暂停/已终止工作台账）。它**是事实源**，这一点和
  status-history 不同：门值、未闭义务、每项停在哪里、恢复条件都在这里。**不进开工必读**，
  只在三种情况下读：恢复某个暂停项、引用某个已终止项的结论、诊断旧决定。
- 移动而非复制，每个值只存一处：
  - `ENDED` 的 Gate board 行整行移入（含 Overall/Lifecycle），状态板上不再有这一行；
  - `PAUSED` 的 Gate board 行，只把四列叙述移入；状态板留一行索引
    `| ID | 简短 Scope | → parked ×4 | Overall | PAUSED |`（模拟均值 175 B），
    Overall/Lifecycle 只存在状态板；
  - 暂停交接行改为一行，停点与恢复条件原文移入；
  - Current state / Immediate next actions / Active constraints 中只涉及非活跃项的段落，
    原文移入对应 work ID 小节；研究轨道约束移入「研究轨道约束（暂停中）」小节。
- 状态迁移：
  - 关闭（→ `ENDED`）：关闭方在同一提交把该行整行移入 parked；
  - 暂停（→ `PAUSED`）：同一提交移走四列叙述、留一行索引；
  - 恢复（→ `ACTIVE`）：状态板行按 O3 上限重写；parked 该节首行加注
    「YYYY-MM-DD 已恢复，现状以状态板为准」，原文不改。
- `check_docs.py`：状态板上出现 `ENDED` 行即拒绝；另外只对 parked 的 ENDED 表执行现有的
  「DONE 行双证据」检查，防止"同一提交置 DONE 并移出"绕过该检查。parked 其余内容不扫描。
- 与既有机制的关系：
  - Log 可压池门行为不变——ENDED 项的 ID 不在 Gate board 上，其条目按"无关联"直接入池，
    结果与现在相同；
  - Gate-echo 只核对 Gate board 上存在的 ID，不会因移出而误报；
  - **须改两处现行规则**：AGENTS.md 与 workflow §6「除 `docs/status-history.md` 这一个单向
    沉淀池外不新增归档系统」一句；以及 `docs/roles/chore.md` 第 13 行「不搬动 Gate board 行，
    不迁移原提案/复核/证据，不新建档案目录或第二份状态账本」。parked 字面上就是第二份状态
    账本，这一点不回避：该规则防的是同一事实两处维护，O1 用"每个值只存一处 + 状态板
    一行索引指明去处"满足其意图，但字面冲突须用户授权修改。分类按 Lifecycle 机械判定，
    不涉及同一行「不自行判定旧工作无参考价值」的禁止。

### O2｜交接一件事只写一处

| 位置 | 每次交接写什么 | 不再写什么 |
|---|---|---|
| Active handoffs 行 | 下一角色、动作、门、必读文件指针（**唯一处**） | 过程叙述、测试数字 |
| Gate board 行（ACTIVE） | 变化的门值 token + 证据文件指针 | 结论叙述 |
| `## Log` 新条目 | 一句结论 + 指针 | 复述复核/证据内容 |
| Current state | 仅在未闭义务增减时改 | 每次交接的进度 |
| Immediate next actions | 仅写交接表表达不了的事（如用户侧待决） | 复述交接行 |

需同步的规则文字：AGENTS.md「共享状态更新」、workflow §6/§6.1、engineering-workflow §10，
以及 `docs/roles/` 中要求更新这些节的句子（落地时逐文件检索）。

### O3｜按字节设上限并机检

| 对象 | 上限 | 检查范围 |
|---|---|---|
| ACTIVE Gate board 行 | ≤ 800 B | 本提交改动过的行（HEAD 中不存在的逐字行） |
| PAUSED Gate board 行 | ≤ 400 B | 全部（落地批次一次压到位） |
| ENDED Gate board 行 | 不得存在 | 全部 |
| 活跃交接行 | ≤ 800 B | 本提交改动过的行 |
| 暂停交接行 | ≤ 300 B | 全部 |
| `## Log` 新条目 | ≤ 600 B（约 200 字） | 本批次新写（沿用可压池门的 HEAD 标题判据） |
| 结构节总字节（`## Log` 之前） | ≤ 30,000 B | 全部 |

- 按字节而不是行数：D1 否决 N6(b) 的理由是它与 chore.md「不以物理行数验收」冲突，
  按字节计没有这个问题。
- ACTIVE 行与活跃交接行只查"本提交改动过的行"：LOOP-001 现有两行（1,976 B、1,791 B）
  本批不碰，下一个改到它们的角色按新上限写。
- 结构节总字节门是稳态控制，防止一次性清理后反弹——COORD-012 N2 的教训正是这个。
- 写不下仍按「内容放错了地方」处理：叙述进复核/证据文件，状态板只留指针。

### O4｜Lifecycle 整理（用户定）

COORD-008/009/010 已落地，改为 `ENDED`，随 O1 移入 parked；其 11 条 Log（78 行）进可压池，
可压池 139 → 217 行，仍在 300 以内。

### O5｜执行方式（用户定）

建议由用户直接授权协调批次、不走接受轮（COORD-008/009/011 均为此形式）。理由：
§6 的验收全部是机检或逐字比对，接受轮的增量拦截价值低于其 token 成本（F8）。
备选：交接受角色 D1 审查。

### 不改的东西

Log 可压池门及其 300 行上限、status-history 的全部规则、任何状态门与 verdict、Gate-echo 语义、
核对轮/复核轮规则、授权账本语义、三条分节行数上限（保留，与 O3 并存）。

## 3. 优化后能节省多少

### 3.1 读取：模拟结果

模拟规则（保守）：段落提及活跃 ID 的保留；**不带任何 work ID 的段落一律保留**；只涉及非活跃
ID 的段落移出；PAUSED 行与暂停交接行替换为一行；ENDED 行移出；On-demand history 加一行
parked 指针（按 220 B 计）。

| 节 | 现（B） | 模拟后（B） |
|---|---|---|
| Gate board | 35,026 | 6,783 |
| Current state | 10,072 | 3,781 |
| Active handoffs | 8,147 | 4,132 |
| Immediate next actions | 5,424 | 4,141 |
| Active constraints | 4,085 | 3,651 |
| Role / On-demand / 文件头 等 | 4,370 | 4,590 |
| **结构节合计** | **67,124** | **27,079（−60%）** |

- token（估算）：每次开工约 1.50–2.09 万 → 0.60–0.84 万，**每次省约 0.90–1.25 万**。
- 移入 parked 约 43,043 B，不进开工路径。
- 进一步空间（估算，不作验收）：模拟没有移走的 SFT-002 过时块余量约 735 B、COORD-007/008/009
  块 760 B、LOOP-001 两行下次改写受 O3 约束后约省 2,167 B、不带 ID 的研究轨道约束人工分类
  约 1.8 KB，合计可到约 **21.5–23.5 KB（−65%~−68%）**。

### 3.2 写入

- 每次交接：均值 7,917 B → O3 上限下最多 **2,200 B**（交接行 800 + Gate board 行 800 +
  Log 600，**−73%**）；典型只改交接行、状态词与一条 Log，约 **1,500 B（−82%）**。
- token（估算）：每次约 0.18–0.28 万输出 token → 0.05–0.08 万。

### 3.3 按一个工作项折算

以 LOOP-001 至今 20 次状态板提交为参照，并假设每次提交约对应一次开工读取（代理口径）：

- 读取：20 × 0.90–1.25 万 ≈ **18–25 万输入 token**；
- 写入：20 × 0.13–0.20 万 ≈ **2.6–4.1 万输出 token**（输出单价通常是输入的数倍）；
- 另有 §6.1「修改前重读待改章节」随节变短同步下降，未计入。

### 3.4 不在本提案范围内

每会话自动加载的 AGENTS.md（17.5 KB）、按需读的 workflow（44 KB，速查层 N5 已被 D1 否决）、
角色细则、提案/复核/证据文件的读取。

4. `check_docs.py` 通过；新增 7 项检查每项配一条修复前必失败的测试（状态板有 ENDED 行、PAUSED

5. 写入复测（报告，不设门）：落地后接下来 10 次交接提交对状态板的写入中位数，目标 ≤ 2,200 B。
