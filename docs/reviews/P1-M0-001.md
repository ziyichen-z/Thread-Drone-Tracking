### Non-blocking

1. **`docs/phase1-single-drone-design.md` §4.3 is stale and contradicts both
   the code and the same document's own §10 R2 entry.**
   [phase1-single-drone-design.md:159](../phase1-single-drone-design.md)
   states "当前 plant 强制 y 速度为零（`BodyCommandReceiver.cs:44`），高度
   自由度暂不可执行" (the plant currently forces y velocity to zero). Reading
   the actual line cited, [BodyCommandReceiver.cs:41-47](../../Assets/TetheredTracking/Scripts/BodyCommandReceiver.cs)
   passes `active.command.velocity_world_mps.y` straight into
   `drone.SetVelocity(...)` — it is not zeroed. `git log --follow` on this
   file shows a single commit (`beba966`, the M0 baseline itself), so this
   restriction never existed anywhere in this repository's history; it is not
   a regression, the doc prose was simply never reconciled with the code it
   describes or with its own §10 R2 row (`phase1-single-drone-design.md:241`),
   which correctly states the y channel "已于 M0 实现." This is also
   confirmed behaviorally: `tests/test_protocol.py:27` asserts
   `body["command"]["velocity_world_mps"]["y"] == 0.1` (nonzero), and the
   Unity log's Body case reports the vertical command actually raised
   altitude (`docs/unity-test-log.md:39`). Recommend Codex delete or correct
   the §4.3 sentence.

2. **Inconsistent NaN/Infinity guarding in `ScenarioConfig.Normalize()`.**
   [ScenarioConfig.cs:159-185](../../Assets/TetheredTracking/Scripts/ScenarioConfig.cs)
   runs `drone.tether_length_m`, `drone.minimum_altitude_m`,
   `drone.maximum_altitude_m`, `drone.maximum_speed_mps`, and
   `drone.maximum_acceleration_mps2` through the `Positive()` helper
   ([ScenarioConfig.cs:188-191](../../Assets/TetheredTracking/Scripts/ScenarioConfig.cs)),
   which explicitly rejects `NaN`/`Infinity` and substitutes a safe default.
   `drone.initial_altitude_m`, `gimbal.maximum_off_nadir_deg`,
   `gimbal.slew_rate_deg_per_second` is the only gimbal field that also uses
   `Positive()`; `sensor.width/height/vertical_fov_deg/capture_hz/jpeg_quality/retained_frame_count`,
   `evaluation.minimum_visible_sample_fraction/tracking_iou_threshold/maximum_pending_frame_count`,
   and `drone.initial_altitude_m` are only passed through `Mathf.Clamp`/
   `Clamp01`, neither of which filters `NaN` (Unity's `Clamp` returns the
   input unchanged when it is `NaN`, since both comparisons are false). A
   strict JSON document cannot encode a literal `NaN` token, so
   `config/scenario.default.json` cannot trigger this, but
   `runtime/scenario_config.json` is documented in `CLAUDE.md` as a
   tool-writable override, and tools such as Python's `json.dump` permit a
   literal `NaN` token by default (`allow_nan=True`). If a future
   config-generation script produced such a value, e.g. for
   `sensor.vertical_fov_deg`, it would silently reach
   `camera.fieldOfView` unguarded. Recommend routing every numeric scenario
   field through the same NaN/Infinity-safe helper.

3. **Self-occlusion avoidance depends on an unenforced ordering invariant.**
   `EvaluationOcclusionGeometry.Build()` finds proxy candidates with
   `FindObjectsByType<MeshRenderer>(FindObjectsInactive.Exclude)`
   ([EvaluationOcclusionGeometry.cs:43-44](../../Assets/TetheredTracking/Scripts/EvaluationOcclusionGeometry.cs)),
   which would also capture the drone hub/arms, tether anchor, and target
   vehicle meshes if they already existed in the scene — all of those have
   their `Collider` destroyed at creation time specifically so they cannot
   occlude their own raycasts. The reason this works today is purely that
   `TetheredScenarioBootstrap.Awake()` calls
   `CreateEvaluationOcclusionGeometry()` before `CreateAnchor()`,
   `CreateDrone()`, and `CreateTarget()`
   ([TetheredScenarioBootstrap.cs:30-33](../../Assets/TetheredTracking/Scripts/TetheredScenarioBootstrap.cs)).
   The invariant is documented only in a code comment
   ([EvaluationOcclusionGeometry.cs:9-11](../../Assets/TetheredTracking/Scripts/EvaluationOcclusionGeometry.cs))
   and is not enforced by an assertion, a name/tag exclusion filter, or a
   test — a future edit that reorders `Awake()`, or a scene that
   pre-populates a drone/target before the bootstrap runs, would silently
   reintroduce self-occlusion colliders with no compile-time or runtime
   signal. Recommend adding an explicit exclusion (e.g. skip renderers under
   the bootstrap's own root transform) as a defense-in-depth measure, not
   just call-order discipline.

4. **Ground-truth box clipping is asymmetric with observation box validation.**
   `ProjectBounds` clips the ground-truth box to the viewport via
   `Mathf.Clamp01` ([CoverageEvaluator.cs:300-304](../../Assets/TetheredTracking/Scripts/CoverageEvaluator.cs)),
   but `TrackingObservationReceiver.Valid()`
   ([TrackingObservationReceiver.cs:103-115](../../Assets/TetheredTracking/Scripts/TrackingObservationReceiver.cs))
   only checks finiteness and `width/height > 0`, not that `x`/`y` stay
   within `[0, 1]` or that the box stays inside frame bounds. For a target
   near the frame edge, a tracker reporting the object's unclipped true
   extent (rather than only its visible portion) would be IoU-scored against
   a ground-truth box that Unity has already truncated at the viewport edge,
   which can suppress `C_track` for reasons unrelated to tracker accuracy.
   This is a legitimate ground-truth-definition choice, not a code defect,
   but worth a conscious decision given `C_track` is the paper's primary
   metric.

**Note 2 — inconsistent `NaN`/`Infinity` guarding in
`ScenarioConfig.Normalize()`.** Reading the full current file
([ScenarioConfig.cs:143-229](../../Assets/TetheredTracking/Scripts/ScenarioConfig.cs)),
every remaining `float` scenario field now routes through the new `Finite()`
helper (line 219-222) or the updated `Positive()` (line 224-228, which now
calls `Finite()` internally rather than duplicating the NaN/Infinity check):
`anchor_world_m` and every `route_world_m[i]` component-wise via the new
`FiniteVector()` (lines 158-165, 209-217), `drone.initial_altitude_m` (line
173-175), `gimbal.maximum_off_nadir_deg` (line 180-182),
`sensor.vertical_fov_deg`/`capture_hz` (lines 187-192), `target.speed_mps`
(line 195-196), and both `evaluation.*` thresholds (lines 197-204). The only
fields still using bare `Mathf.Clamp` without `Finite()` are `int` fields
(`sensor.width/height/jpeg_quality/retained_frame_count`,
`evaluation.maximum_pending_frame_count`), which is correct — a C# `int`
cannot hold `NaN`/`Infinity`, so no guard is needed there. `FiniteVector`'s
route-fallback indexing (`fallback.target.route_world_m[index %
fallback.target.route_world_m.Length]`) correctly wraps when a custom route
has more waypoints than the 8-point built-in default, avoiding an
index-out-of-range. I checked the one aliasing edge case this introduces —
when the loaded config omits `anchor_world_m` entirely, line 149 first aliases
it to the same object as `fallback.anchor_world_m`, so `FiniteVector` at line
158 is called with `value` and `fallback` as the identical reference; this is
benign because `CreateDefault()`'s literals are always finite, so the
self-referential `Finite(x, x)` never has a non-finite input to guard against.
This closes the note completely: no numeric path from a parsed override to
Unity transforms/camera/physics is unguarded anymore. **Resolved**, with
matching empirical evidence: `docs/unity-test-log.md`'s
`UT-P1-M0-001-002` "Non-finite config" case reports a scenario override with
`1e100` values (a standards-conforming, finite-as-written JSON number that
overflows a 32-bit `float` to `Infinity` on parse — a more realistic trigger
than the literal `NaN` token I originally worried about, since standard JSON
cannot encode `NaN`) resulted in the drone camera sitting at `(132, 25.2,
117)` — exactly `anchor (132, 0.2, 117) + up * default initial_altitude_m
(25)` — and vertical FOV `60`/thresholds `0.2`/`0.3`, i.e. every affected
field fell back to its documented default. The log also candidly records that
the reviewer's first attempt at `1e999` was rejected by Unity's JSON parser
before it ever reached a `float` (JSON `double` overflow, not the guard under
test), and was corrected to `1e100` to actually exercise the new per-field
checks — I take this as evidence of careful, non-cherry-picked
regression testing rather than a weakness.

**Note 3 — unenforced self-occlusion ordering invariant in
`EvaluationOcclusionGeometry`.** The fix is stronger than what I asked for.
`Build()` now takes `params Transform[] excludedRoots`
([EvaluationOcclusionGeometry.cs:28-39](../../Assets/TetheredTracking/Scripts/EvaluationOcclusionGeometry.cs))
and throws `ArgumentException` if the array is null, empty, or contains a
null entry — so a future caller cannot silently build proxies with zero
exclusions. `IsExcluded()` (lines 110-117) matches a candidate renderer's
transform against each root by reference or `IsChildOf`, incrementing
`ExcludedRendererCount` before any candidate/proxy accounting happens (lines
55-65), so excluded actors never inflate `CandidateRendererCount` and can
never receive a proxy. `TetheredScenarioBootstrap` now captures
`anchorVisual` at anchor creation
([TetheredScenarioBootstrap.cs:79](../../Assets/TetheredTracking/Scripts/TetheredScenarioBootstrap.cs))
and calls `CreateEvaluationOcclusionGeometry()` *after* `CreateAnchor()`,
`CreateDrone()`, and `CreateTarget()`
([TetheredScenarioBootstrap.cs:31-34](../../Assets/TetheredTracking/Scripts/TetheredScenarioBootstrap.cs)),
passing `anchorVisual, Drone.transform, Target.transform` explicitly (line
52) and throwing `InvalidOperationException` first if any of the three is
still null (lines 49-51). This replaces implicit call-order fragility with an
explicit, enforced contract: even if a future edit reorders `Awake()` again,
proxies still cannot be built without naming exclusion roots. I independently

renderers. The remaining runtime-created object with a visual, `TetherLine`
([TetheredScenarioBootstrap.cs:108-111](../../Assets/TetheredTracking/Scripts/TetheredScenarioBootstrap.cs)),

the 1+5+2 arithmetic above, which is strong corroborating evidence that the
code path the log describes is the code path I read.

**Note 4 — ground-truth/observation box-clipping asymmetry.** Codex chose the
policy I asked for a decision on: tracker boxes must represent the
image-clipped visible extent, matching how `ProjectBounds` already clips
ground truth. `TrackingObservationReceiver.Valid()`
([TrackingObservationReceiver.cs:113-118](../../Assets/TetheredTracking/Scripts/TrackingObservationReceiver.cs))
now additionally requires `box.x >= 0f`, `box.y >= 0f`, `box.x + box.width <=
1f`, and `box.y + box.height <= 1f`, on top of the pre-existing
finite/positive-size checks. `controller/tracking_entry.py`'s `observation()`
([tracking_entry.py:33-39](../../controller/tracking_entry.py)) enforces the
identical inequality before ever calling `atomic_write`, so an out-of-frame
box never reaches disk from the reference publisher — defense in depth against
a future non-Python client that might write the file directly. Both sides use
the same four-inequality definition, so there is no longer a gap between what
ground truth clips to and what predictions are allowed to claim. **Resolved**,
verified by: (a) reading both files directly, (b) re-running
