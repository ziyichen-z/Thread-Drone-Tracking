# 工程工作流（engineering-v1）

本文定义工程轨道（`Workflow: engineering-v1`）的工作方式。换轨依据、旧项
处置理由与迁移验收项留在
`docs/proposals/COORD-010-engineering-transition-and-data-closeout.md`，本文
不复制；本轨道的生效状态以 `docs/current-status.md` 的 `COORD-010` 行为准，
本文不自证生效。本文只写现行规则，各条规则的来历见
`docs/workflow-changelog.md`。

## 0. 适用范围与路由

- **适用**：提案抬头逐字写有 `Workflow: engineering-v1` 且**经接受角色在
  `ACCEPTED` 时裁定生效**的工作项，按本文执行。该行本身只是申请，构思/实现
  角色不得自行判定轨道。本文**只替换** COORD-010 §6 机制表逐行列出的那 11 项机制
  （任务合同、提案与决策、日常实现、必经停点、复核收敛、测试、数据核验、
  资源与并发、状态板体量、完成/终止、独立设计审查）；`AGENTS.md` 与
  `docs/collaboration-workflow.md` 中未被本文逐条替换的规则对工程轨道全部
  继续适用——**本文未提及不等于豁免**。点名仍然有效的至少有：授权账本与
  信封纪律、Unity 真值只允许进入 `CoverageEvaluator`、可派生标识禁手写、
  诊断验证通道与人眼保真检查（workflow §4.3.2）、复核开轮资格与
  PLAY_GOVERNING 唯一定义、finding 分级与六值依据列、收工前
  `check_role_writes.py` 与更新状态板后 `check_docs.py` 的自检。
- **缺省（fail-closed）**：没有该行、申请被驳回、`Workflow:` 取值不在闭集
  （当前闭集只有 `engineering-v1`）、或接受角色未写明裁定的工作项，一律走
  旧流程（`AGENTS.md` + `docs/collaboration-workflow.md`）并停下问接受角色，
  不按本文放宽。**既有 work ID 一律不得追加该行**。
- **旧工作**：COORD-010 §3 表内的工作项只执行该表具名的终止或延期动作；
  其历史实现、复核轮次、verdict 与证据不回溯套用本文规则，也不因本文改判。
  凡未逐字标注路由行的工作项一律走旧流程，包括全部既有 `P1-*` 与 `COORD-*`
  工作项、里程碑 M0–M7 及投稿相关工作；本文不给出「哪些算研究轨道」的枚举，
  判据只有路由行在不在，以及接受角色是否在 `ACCEPTED` 时写明裁定；缺任一即
  研究轨道。
- 工作 ID 命名与轮次命名（设计轮 `D<n>`、核对轮 `C<n>@<停点>`、复核轮
  `R<n>@<停点>`）沿用旧流程；`<停点>` 取本文 §4 的 K1–K5 短名，提交信息主题
  仍以 `<work-id> <轮次>` 开头。

## 1. 职责保持

实现角色写代码与测试；接受角色做范围决策、只读核对与收口；复核角色不修
代码、不复核自己的实现；用户给出关键授权及 Unity/硬件反馈。角色边界与
`docs/roles/` 写入白名单不因工程轨道放宽：接受角色和复核角色在本轨道同样
没有运行时代码写权限，复核发现缺陷的唯一合法动作仍是写复核文件。

## 2. 任务合同

- 一个工作项一份短说明：目的、范围、接口、验收项、预算、限制。
- 验收项用稳定编号 `AC-n`，表列集与 `docs/proposals/README.md` 的工程模板
  一致：`编号 | 验收项（可证伪） | 证据指针 | 停点 | 日期`；证据指针带
  `test:` / `artifact:` / `cmd:` 前缀（与旧流程同口径）。
- 工程工作项不要求旧流程的七列 BC 表，也不受 `NEW_OBLIGATION` 每工作项
  2 条的配额约束；这只免除记账形式，不免除「先确认再实现」。相应地：复核
  finding 的依据列**不新造 token**：闭集六值（`BC-n` / `IN_SCOPE_NO_BC` /
  `SCOPE_GAP` / `上轮漏检` / `上游漏检` / `RED_LINE`）逐字沿用，依据列仍写
  `BC-n`，在工程轨道读作任务合同第 n 条验收项 `AC-n`，对应关系写在 finding
  正文；`IN_SCOPE_NO_BC` 读作「可达、在范围内但无 `AC-n` 覆盖」。workflow
  §4.6 的归因派生与「范围外已知缺陷」记债因此无须改动。工程轨道不要求研究
  轨道 BC 表下的 `复核项覆盖：` 行（与提案 §6、`docs/proposals/README.md` 的
  工程模板及各角色细则一致）。
- 接口或验收项的实质变化必须先记录并由接受角色确认，不能边实现边解释扩大
  范围；改变目标、硬件目标或资源边界仍须回到用户。

## 3. 提案与决策

- 提案文件只保留当前正文加一段简短决策记录，不强制逐 D 轮叙述章节，轮次
  叙述进提交信息。
- 接受角色确认范围与边界；目标、硬件目标、资源额度与公开发布由用户决定。
- 退修上限不变：同一范围第二次退修后仍上交用户二选一（接受当前范围并逐条
  列出已知缺口，或关闭为负结果记录），不得无限循环。决策信封 D1 在效、
  残留数非递增（本轮不多于上一轮；裁定节末 `open_items:` 机读行，自首次退修裁定起每轮必填；
  COORD-015 §5.1/BC-12，COORD-016 §2.1/BC-1）且本提案已代拍少于 3 次时改交 supervisor，supervisor 仅可代选 (a)；否则仍
  上交用户。

## 4. 日常实现与必经停点 K1–K5

已接受任务范围内的小改由实现角色自行 focused 验证，相关改动可合并到下一个
稳定停点，不逐提交走核对轮/复核轮。未经独立复核的中间成果只记
`IMPLEMENTED`，不记 `DONE`。

| 停点 | 触发 |
|---|---|
| `K1` | 帧/控制协议，及坐标与时间语义 |
| `K2` | 安全约束与控制命令 |
| `K3` | 模型决策、目标身份与重播种 |
| `K4` | 数据划分、标签，或对外指标 |
| `K5` | 对外发布候选 |

- 每个停点保留接受角色的只读核对轮 `C<n>@K<i>` 与独立复核轮 `R<n>@K<i>`；
  核对轮不跑测试、不改实现、不签发独立复核（细则不变，见 workflow §4.3.3）。
- 相互关联的触发可以合并为同一个候选走一次停点，但不得以「工程轨道」为由
  豁免其中任何一项关键检查。
- 到达停点后实现角色停止启动依赖该结果的后续实现，先整理候选与证据。
- 候选含**不可重跑的消耗步骤**（次数或额度一次性耗尽的硬件正式轮、租云、限量查询
  等）时，该步骤所依赖的代码先过一次停点（核对轮加独立复核）再消耗，消耗产出的证据
  另过停点。未先复核即已消耗的，其后的补丁须在证据中写明未在真实条件下验证。

## 5. 复核收敛

- 每个停点产出一份核对表和一份复核文件：核对表写在该工作项提案/任务合同的
  固定小节 `## Contract conformance（核对表）`（只留最新一版），复核文件写
  `docs/reviews/<work-id>.md`（`tools/check_docs.py` 第 4 项按 Gate board 的
  work ID 同名核对）。两者记录候选、结论与未闭问题；复核 `REWORK_REQUIRED`
  的修复直接回复核，不经核对轮。
- 计数、上限、机读行与 `blocks_consuming_gate` / `releases_consuming_gate`
  配对**全部不变**，见 workflow §4.4 与 AGENTS.md「共享状态更新」；未 release
  的 block 继续阻断消耗性交接。
- 「减少记账」不等于可以无限复查：范围外的新主张不在返工轮里追加。

## 6. 测试

- 开发期只跑 focused 套件；停点跑一次全套，输出写 `docs/evidence/` 下的证据
  文件，上下文只回显摘要，不带 `-v`。
- 全套结果必须区分并写明基线已有失败与本批次新增失败。
- 停点全套所需的本机模型加载与数据回放属预算信封维度：提案按「每个候选 1 次、至多
  N 个候选」列明执行机器与次数上限，随信封一次签发，不逐候选另签；超出所列上限仍
  回到用户。
- 相对上一个已跑过停点全套的候选只改动具名文件的窄修，可用覆盖改动文件的 focused
  套件加所修 finding 的修前红/修后绿，代替该候选的停点全套（workflow §4.3.1
  条件 2）；前提是改动不触及真实模型加载器、数据划分或对外指标路径。证据文件列出
  改动文件并写明未跑全套、不记全套通过；复核角色可判替代不足并要求全套。
- 复核角色的重跑范围不变：focused 套件一次并记录测试树哈希，加每条阻断
  finding 的修前红/修后绿一次；全套自动测试仍是实现者的停点证据义务，不是
  复核开轮义务。核对角色不跑实现测试。
- 基础设施工具（`tools/check_*.py` 等）有自己的聚焦回归，不并入功能套件的
  停点证据。

## 7. 数据核验

- 新导入、加工或迁移数据时自动核对完整性与来源（计数、哈希、来源指针）；
  候选未改变时不人工重复全量核验。
- 标签按错误风险分层抽查：完整性核验与语义抽查互补，不用固定「看 N 张」替代
  完整性核验，也不用完整性核验替代语义抽查。
- 旧归档合同与既有 manifest 不回改；派生产物记录来源与修订依据，原始工件
  不覆盖。

## 8. 资源与并发

多角色分工与并发纪律在工程轨道上与研究轨道相同：

- Active handoffs 上限仍为 **每路 1 条消耗性 + 2 条零消耗**活跃交接（双路
  `fast`/`vlm`，COORD-019），交接表 `Consuming` 与 `Lane` 列逐行声明。（数值与判据的权威定义在 `AGENTS.md`「执行轨道
  纪律」与 `tools/check_docs.py`，本文只引用、不另立。）
- supervisor 接力调度（COORD-015 §3.1）在本轨道同样适用：每路（`fast`/`vlm`）
  同一时刻最多 1 个写仓库的角色、两路可并行（COORD-019 补充），被拉起的实现
  子代理按现行规则消耗与记账。
- **Gate-echo** 机检不变：交接内引用的、在 Gate board 有行的反引号标识必须以
  `` `<ID>`@<Overall> `` 形式逐字携带当前 Overall token。
- **共享槽位互斥**：Play/采集操作单沿用的共享槽位互斥使用约定按现状保留
  （`AGENTS.md`「工作流轨道路由」、workflow §7 规则 0），不另立条文；
  两个角色不同时修改同一实现文件、复核角色只在一次性 worktree 接触
  实现代码是 workflow §7 规则 3，在本轨道同样不变。
- 每个工作项一份预算信封，信封只能由用户授权给出并逐字记入
  `docs/authorizations.md`；字段与 `AGENTS.md` 授权信封同口径（阶段、尝试
  次数上限、GPU·h 上限、API 次数上限、Unity/Play=否），**缺项视为 0**。
  信封内的工程性重试与 supersession 不需要重复授权，由接受角色在该工作项
  任务合同的决策记录里记一行归因（工程轨道免除 BC 表后，这一行是信封归因的
  唯一落点）；任何越界回到用户。已无待执行动作的记录离开 Active
  handoffs，但预算与锁的保护不删除。

## 9. 硬件与端侧探测（Jetson）

Jetson 小规模可行性探测可以前移，但仍须独立立项、独立说明设备与额度。

- 前移只改顺序，不改门槛：探测作为独立工作项提出，写明设备型号、可用额度与
  预期产出，取得用户单独授权后才动用任何硬件或下载额度。
- **桌面量化结果不能替代板端实测**：没有板端实测证据时，不得声称任何 Jetson
  性能、时延或显存结论。
- 工程首版不承诺 Jetson 性能；相关主张只能来自该独立工作项自己的证据。
- **先核环境事实再定合同**：合同与信封所依赖的端侧环境事实（解释器与包、推理栈版本
  与架构支持、编译工具链、磁盘与内存余量、链路）须有零消耗只读预检的原始读数，写入
  提案「只读试读」节；未核实的逐条标为假设，凡依赖未核实假设的额度维度，在该假设
  核实前不申请签发（按缺项为 0）。设备暂不可达时，只读预检列为工作项第一步，其余
  维度待预检结果回来再申请签发。

## 10. 状态板体量

- `docs/current-status.md` 只放当前工作（活跃项的 Gate board 行、下一动作与
  未闭义务）与非活跃项的一行索引；非活跃项详情在 `docs/parked-status.md`；
  写入分工与字节上限见 `AGENTS.md`「共享状态更新」；过程叙述归
  `docs/reviews/`、`docs/evidence/`、`docs/design-reviews/` 和
  `docs/unity-test-log.md`。
- 分节上限保留：Current state ≤ 100 行、Immediate next actions ≤ 50 行、
  Active handoffs ≤ 70 行。（数值与判据的权威定义在 `AGENTS.md`「共享状态
  更新」与 `tools/check_docs.py` 的 `SECTION_LINE_CAPS`，本文只引用、不另立。）
- 全文不设行数硬阻断；体量规则以 `AGENTS.md`「共享状态更新」、
  `docs/collaboration-workflow.md` §6 与 `tools/check_docs.py` 的正文为准，
  本文不自行改动旧流程的体量规则。chore 常设内容维护按
  `docs/roles/chore.md`「允许的任务」统一执行，包括旧 Log 的压缩、旧 Log
  删除条件与引用处理。保留指针、结论与未闭义务，
  禁止为腾空间压缩本批次新条目或删减他人未沉淀的内容。
- 除 `docs/status-history.md` 这一个单向沉淀池与 `docs/parked-status.md` 这一份
  非活跃项台账外不新增归档系统（移出的叙述移动
  而非复制、移入前须经用户按 work item 一次同意，git 历史仍是权威档案），也不把
  完整过程复制进状态板。
- 开工与历史依据按 `docs/collaboration-workflow.md` §6.1 轻量按需读取；
  复用资产先读工程继承清单和缺陷账本，K1–K5 的必读候选与证据范围不缩减。

## 11. 完成与终止（硬约束）

- `DONE` 仍须三样齐全：实现者证据 + 独立复核通过 + 相应的 Unity/硬件证据。
  `IMPLEMENTED` 不等于 `DONE`（细则见 AGENTS.md「完成规则」）。
- 纯离线、不影响 Unity 运行行为的事项可用 `UNITY_NA`，必须写明理由并经
  **复核角色在复核文件中附议**；工程轨道不放宽这一条。
- `CLOSED_*` 表示明确停止该范围的工作，**不可冒充通过**，不替代 `DONE`，也不
  产生任何研究主张。
- 历史负结果、既有主张上限、`blocks_consuming_gate` 与
  `releases_consuming_gate` 的配对全部继续有效，不因换轨清除。
- 工程首版发布以自己的工作项记录，**不借用旧里程碑的关闭名义**，也不声称
  完成了被延期的研究工作。

## 12. 独立设计审查

- 新工程工作按 K1–K5 做相称的设计检查，检查者不得是该候选的实现者。
- 恢复旧 M2/M5 或投稿研究时仍受原设计审查门约束（workflow §4.7）：审查者
  不得是相关提案作者，也不应是该设计的主要接受/实现者。
- 工程轨道的检查不替代到期的研究设计审查，也不得声称其已完成。

## 13. 本文件的修改权限

本文件属工作流基础设施，与 `AGENTS.md`、`CLAUDE.md`、
`docs/collaboration-workflow.md`、`docs/roles/`、`tools/check_*.py`、
`tools/githooks/` 同级：所有角色会话只读，只有用户直接授权的协调批次可以
修改，由 `tools/check_role_writes.py` 的 `INFRA_PATTERNS` 机械保护。与旧
流程的硬门（完成规则、Unity 真值隔离、写入白名单、授权账本）冲突时以旧流程
为准，本文不得被解读为其豁免。
